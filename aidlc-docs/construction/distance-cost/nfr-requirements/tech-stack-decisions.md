## 3. 決定 1: NumPy を使わない（Q1=A）

### 3.1 根拠

距離行列の計算量は、小学校区数 `D` に対し `D(D+1)/2` 回の Haversine 計算である。

| `D` | 計算回数 |
|:---:|:--------:|
| 100 | 5,050 |
| 200 | 20,100 |

Haversine 1 回は三角関数を数回呼ぶだけである。**2 万回でも素朴な Python ループで 1 秒未満で終わる。**

### 3.2 NumPy を入れないことの利点

- **U-02 のプロダクション依存はゼロを維持する。** SECURITY-10 の脆弱性スキャン対象を増やさない
- **リンタ規則 R-3 を緩めなくてよい。** `src/distance_cost/` は `src/shared_kernel/` 以外を import しない、という契約がそのまま保てる
- U-02 が純粋関数であること（NFR-M02）が、標準ライブラリのみで自然に達成される

### 3.3 U-01 の文書への影響

U-01 の `tech-stack-decisions.md` セクション 11 は、依存一覧に `numpy` を「距離行列の事前計算」用途で挙げていた。**本決定により不要と判明したため、当該エントリを取り消し線で更新した**（承認済み文書の訂正）。

**NFR-P03 の「事前計算」の主眼**: 性能ではなく、**キャッシュによる再計算の回避**である。US-14 で担当者が迂回係数・平均速度・費用モデルを変えるたびに大円距離を再計算しないよう、大円距離をキャッシュする（Q3=A の U-02 Functional Design）。大円距離は座標のみに依存するため、これらのパラメータ変更では無効化されない。

## 4. 決定 2: オラクルは表を埋め込む（Q2=A）

### 4.1 なぜオラクル検証が必要か

P-D05（PBT-05）。**対称性（INV-07a）と非負性（INV-08a）のプロパティは、誤った Haversine 実装でも成立する。**

| 実装誤り | 対称性 | 非負性 | オラクル |
|---------|:------:|:------:|:--------:|
| 緯度と経度を取り違える | ✅ 成立 | ✅ 成立 | ❌ **検出** |
| `atan2` の引数を逆にする | ✅ 成立 | ✅ 成立 | ❌ **検出** |
| 度をラジアンに変換し忘れる | ✅ 成立 | ✅ 成立 | ❌ **検出** |

プロパティだけでは、これらの誤りをすべて見逃す。**独立した測地線距離との比較（オラクル）だけが捕まえる。**

### 4.2 表による実装

既知の座標ペアと、公表されている実距離（大円距離または測地線距離）の表をテストに埋め込む。

| ペア | 座標 | 参考距離 |
|------|------|---------|
| 東京駅 〜 大阪駅 | (35.681, 139.767) 〜 (34.702, 135.495) | 約 403 km |
| 東京駅 〜 横浜駅 | (35.681, 139.767) 〜 (35.466, 139.622) | 約 27 km |
| 東京駅 〜 名古屋駅 | (35.681, 139.767) 〜 (35.171, 136.882) | 約 270 km |
| 札幌駅 〜 福岡駅 | (43.068, 141.351) 〜 (33.590, 130.421) | 約 1,415 km |
| 同一点 | (35.681, 139.767) 〜 (35.681, 139.767) | 0 km |

**許容誤差 0.5%**（球体近似と楕円体測地線距離の差）。実際の座標と距離は Code Generation ステージで検証・確定する。

### 4.3 geopy を使わない理由

`geopy` は任意の座標ペアで測地線距離を計算でき、プロパティテストで無数のペアを検証できる。しかし:

- **テスト依存が 1 件増える**
- **実装誤りの検出には、少数の既知ペアで十分である**。取り違え系の誤りは、東京〜大阪のような遠距離ペア 1 つで数百 km の乖離として現れる

表は追加依存なしで、この検出力を得られる。

## 5. 決定 3: 事前計算の責務分担（Q3=A）

```text
  U-02 distance-cost                        U-03 data-management
  +------------------------------------+    +----------------------------+
  |  compute_district_distance_matrix( |    |  小学校区マスタ更新を検知  |
  |    districts                       |<---|  再計算を起動              |
  |  ) -> list[DistanceCacheEntry]     |    |                            |
  |  純粋関数                          |--->|  結果を DB に永続化        |
  +------------------------------------+    |  (P-03 の実装)             |
                                            +----------------------------+
```

| 責務 | ユニット |
|------|---------|
| 距離行列の計算（純粋関数） | **U-02** |

**U-02 は「いつ再計算するか」を知らない。** それは永続化と業務フローの問題であり、U-03 の責務である。U-02 は「与えられた小学校区群に対する距離行列」という純粋な写像を提供するだけである。

**申し送り U02-H10**: U-03 は `compute_district_distance_matrix()` を呼び、結果を永続化すること。再計算の起動契機は小学校区マスタの更新時のみ（US-09）。

## 6. 決定 4: 浮動小数点の再現性（Q4=A）

**INV-07b（キャッシュ経由の厳密等価）は、同一プロセス内でのみ保証する。**

### 6.1 保証すること

同一プロセス内で、`cached_distance(a, b)` と `cached_distance(b, a)` は**ビット単位で同一**である。

**根拠**: キーの正規化 `(min(id), max(id))` により、両方向が同一のキャッシュエントリを引く。これはデータ構造の性質であり、浮動小数点演算の性質ではない。**環境に依存しない。**

### 6.2 保証しないこと

異なる実行環境（CPU、Python バージョン、コンパイルオプション）の間で、Haversine 計算の最下位ビットが一致すること。

**根拠**: これは過剰である。キャッシュは環境ごとに再計算される。異なる環境で計算した大円距離が最下位ビットまで一致する必要はない。INV-07a（許容誤差 ε = 1e-9 km）で、生の Haversine の対称性は環境に依存せず成立する。

### 6.3 プロパティテストへの影響（PBT-08）

- **INV-07b のプロパティテストは、同一プロセス内で `cached(a,b) == cached(b,a)` を厳密等価で検証する**。キーの正規化により常に成立する
- **INV-07a のプロパティテストは、生の Haversine を許容誤差 ε で検証する**。環境非依存
- **P-D05 のオラクルテストは、許容誤差 0.5% で表と比較する**。環境非依存
