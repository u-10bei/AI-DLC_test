## 2. スコープ A: U-01 固有の非機能要件

U-01 は**型定義のみ**を持ち、稼働するプロセス、永続化、ネットワーク通信のいずれも持たない。

### 2.1 該当しない NFR カテゴリ（根拠付き）

| カテゴリ | 判定 | 根拠 |
|---------|:----:|------|
| スケーラビリティ | **N/A** | 負荷を受けるコンポーネントを持たない。型定義はコンパイル時に解決される |
| 性能（応答時間、スループット） | **N/A** | 唯一の振る舞い `effectiveDeclarationFor()` は、1 職員の申告履歴（実務上は高々数件）を線形走査するのみ。計算量は O(n)、n は再申告回数 |
| 可用性（稼働率、RTO、RPO） | **N/A** | 稼働するプロセスを持たない。加えてレジリエンシー拡張は無効（CQ4=A）であり、PoC 全体として SLA を定めない（Q10=A） |
| ユーザビリティ | **N/A** | UI を持たない |

### 2.2 該当する NFR

#### NFR-U01-R01: fail closed の生成時バリデーション（信頼性）

**要件**: 不変条件を満たさない値オブジェクト・エンティティは、生成そのものを拒否する。部分的に構築されたオブジェクトや、既定値で埋めたオブジェクトを返してはならない。

**根拠**: SECURITY-15（例外処理と fail-safe デフォルト）。`business-rules.md` の BR-01〜BR-07。

**検証方法**: プロパティベーステスト P-03, P-04, P-05, P-08（不正な入力に対して生成が失敗すること）。

**実現手段**: 例外を送出する（Q6=A）。詳細は `tech-stack-decisions.md`。

---

#### NFR-U01-R02: 型の破壊的変更の管理（保守性）

**要件**: U-01 の型は U-02〜U-07 の 6 ユニットから参照される。型の破壊的変更は、CI で機械的に検出されなければならない。

**根拠**: `unit-of-work-dependency.md` の依存マトリクス。U-01 は依存グラフの根である。

**実現手段**（Q11=A）:
- 静的型チェッカ（`mypy` strict モード）を CI で強制する
- ユニット境界のリンタ規則 R-1〜R-6 を CI で検証する

**R-3 の重要性**: `src/distance-cost/` は `src/shared-kernel/` 以外を import してはならない。この規則が守られる限り、`C-01 DistanceCostCalculator` は構造的に純粋関数であり続ける（NFR-M02）。

---

#### NFR-U01-R03: 個人情報の型レベルでの隔離（セキュリティ）

**要件**: `Staff.name` と `Staff.residenceDistrictId` は個人情報である。これらがログ・エラーメッセージ・監査ログに出力されてはならない。

**根拠**: SECURITY-03、NFR-S02。

**実現手段（構造による保証）**:
- `U-06 security` は U-01 から**識別子の型のみ**（`StaffId`, `EventId`, `FacilityId`）を利用し、`Staff` エンティティ自体を参照しない
- したがって U-06 のコードから `Staff.name` を読む経路が**存在しない**
- エラーメッセージには職員 ID のみを含める（`business-rules.md` セクション 4.3）

**検証方法**: リンタ規則により、`src/security/` が `Staff` を import していないことを検証する。

---

#### NFR-U01-R04: 数値精度（信頼性）

**要件**:

| 値 | 型 | 根拠 |
|----|----|------|
| `TravelMetrics.distanceKm` | 倍精度浮動小数点 | 許容誤差 ε = 1e-9 km で対称性を検証する（INV-07a） |
| `TravelMetrics.timeSeconds` | 非負整数（秒） | 分単位に丸めると 2,000 人分の集計で最大約 17 時間の誤差が生じる |
| `TravelMetrics.costYen` | 倍精度浮動小数点 | 内部は実数。表示・エクスポート時のみ整数円へ丸める（Q5=B, Q7=A） |

**倍精度で十分である根拠**: 倍精度は約 15 桁の有効数字を持つ。距離単価を 400 円/km、最大距離を 100 km と仮定しても 1 件あたり 4 万円、2,000 人分で 8,000 万円。この規模で円未満の誤差が累積しても、集計結果への影響は無視できる。

**MILP ソルバーとの整合**: ソルバーは目的関数の係数を浮動小数点で受け取る。`Decimal` を用いてもソルバー内部で浮動小数点へ変換されるため、精度上の利益がない（Q7=A の却下理由）。

### 3.4 SECURITY-14 の実現手段（PoC）— 詳細

#### 問題

Application Design の Q6=A は「アプリケーションのアカウントに削除権限を与えない」ことで監査ログの改竄を防ぐと定めた。PostgreSQL であればロールと権限で実現できる。

しかし **SQLite にはユーザーもロールも存在しない**。ファイルを開ける者は、その中のあらゆるテーブルを `DELETE` も `DROP` もできる。**この統制は SQLite 上では実現できない。**

#### 採用する実現手段（Follow-up Q1=A）

監査ログを **JSON Lines 形式のファイル**に追記し、Linux の **追記専用属性（`chattr +a`）** を付与する。

| 操作 | 属性なし | `chattr +a` |
|------|:-------:|:-----------:|
| ファイル末尾への追記 | ○ | **○** |
| 既存行の書き換え | ○ | **×** |
| ファイルの切り詰め（truncate） | ○ | **×** |
| ファイルの削除・改名 | ○ | **×** |

`CAP_LINUX_IMMUTABLE` を持たないプロセス（＝アプリケーション）は、**追記のみ可能**である。

**この設計の利点**:
- `P-04 AuditLogPort` が削除・更新のメソッドを定義しないという型レベルの設計と、OS レベルの強制が二重に働く（defense in depth、SECURITY-11）
- **PoC と実運用で同一の仕組みが使える**。DB を PostgreSQL へ移行しても、監査ログの統制を再設計しなくてよい

**制約と、それに伴う要件**:

- 追記専用ファイルは、アプリケーションからローテーション・切り詰めができない
- **SECURITY-14 は最低 90 日の保持を要求する**。保持期間の管理は、アプリケーション外の特権プロセス（cron 等）が行う
- **これは Infrastructure Design の対象である**（申し送り U01-H16）

**前提**: ファイルシステムが `chattr +a` に対応すること（ext4, XFS 等）。属性の付与には root 権限が必要である。

### 3.5 非同期ジョブ基盤の必須設定（Follow-up Q2=A）

SQLite 上で DB バックエンドのジョブキュー（Q5=A）を成立させるため、以下を**必須設定**とする。**推奨ではない。**

| 設定 | 値 | 理由 |
|------|----|------|
| `PRAGMA journal_mode` | **`WAL`** | 読み取りと書き込みを並行させる。既定のロールバックジャーナルでは、書き込み中に読み取りがブロックされる |
| `PRAGMA busy_timeout` | **5000（ms）以上** | 書き込み競合時に即座に `database is locked` で失敗せず、待機する |
| `PRAGMA foreign_keys` | **`ON`** | SQLite は既定で外部キー制約を強制しない。参照整合性（`Staff.departmentId` など）の検証に必要 |

**加えて、Application Design で既に定めた規則を再掲する**: **最適化の計算はトランザクション外で実行する。** 300 秒の計算中に書き込みトランザクションを保持すると、SQLite の単一ライタ制約により API リクエストがブロックされる。

**構成上の前提**: 単一サーバー（A-07）、単一のジョブワーカープロセス。これにより書き込み競合は限定的である。
