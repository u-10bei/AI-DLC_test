# ドメインエンティティ — U-02 `distance-cost`

**作成日**: 2026-07-09
**ステージ**: CONSTRUCTION - Functional Design（ユニット 2 / 8）

---

## 1. U-02 は新たなエンティティを定義しない

U-02 が扱う型は、**すべて U-01 `shared_kernel` が既に定義している**。

| 型 | 定義元 | U-02 での用途 |
|----|-------|-------------|
| `Coordinates` | U-01 | Haversine 距離の入力 |
| `SchoolDistrict` | U-01 | 代表点の保持 |
| `SchoolDistrictId` | U-01 | キャッシュキー |
| `TravelMetrics` | U-01 | 算出結果（距離・時間・費用） |
| `TravelParameters` | U-01 | 迂回係数、平均速度、同一校区固定時間、**費用モデル** |

これは U-02 が依存グラフ上 U-01 の直下にあることの帰結である。U-02 は**関数**を提供するユニットであって、**型**を提供するユニットではない。

## 2. U-01 に追加する型（承認済みコードの修正を伴う）

**Q1=A（距離帯モデルの採用）により、`TravelParameters` の費用パラメータを差し替える必要がある。**

### 2.1 なぜ U-01 に置くのか

`CostBand` は `TravelParameters` のフィールドとして参照される。`TravelParameters` は U-01 に属する。

したがって `CostBand` を U-02 に置くと、**U-01 が U-02 を import する**ことになる。これは以下に違反する。

- リンタ規則 **R-2**（`shared_kernel` は他のいかなるユニットも import してはならない）
- 依存グラフの非巡回性（U-01 は依存グラフの根である）

**したがって `CostBand` と `CostModel` は U-01 `src/shared_kernel/value_objects.py` に追加する。**

### 2.2 削除する型

| 型 / フィールド | 理由 |
|----------------|------|
| `TravelParameters.unit_price_per_km: float` | 線形モデル専用のパラメータ。距離帯モデルでは不要 |

### 2.3 追加する型

#### `CostRule`（列挙型）

各距離帯における費用の算出方式。

| 値 | 意味 |
|----|------|
| `FLAT` | 一律の固定額（距離に依存しない） |
| `PER_KM` | 距離に比例（距離 × 単価） |

#### `CostBand`（値オブジェクト、frozen）

| 属性 | 型 | 説明 |
|------|----|------|
| `upper_bound_km` | `float \| None` | この帯の上限（**排他的**）。`None` は無限大を表す（最上帯） |
| `rule` | `CostRule` | 費用の算出方式 |
| `amount_yen` | `float` | `FLAT` なら固定額。`PER_KM` なら 1 km あたりの単価 |

**生成時バリデーション**:
- `upper_bound_km` は正、または `None`
- `amount_yen` は非負

#### `CostModel`（値オブジェクト、frozen）

| 属性 | 型 | 説明 |
|------|----|------|
| `bands` | `tuple[CostBand, ...]` | 下から順に並んだ距離帯 |

**生成時バリデーション**（詳細は `business-rules.md` の BR-D04）:

1. 帯が 1 つ以上ある
2. `upper_bound_km` が**厳密に単調増加**している
3. **`None`（無限大）を持つ帯はちょうど 1 つで、それは最後の帯である**
4. **費用関数が距離に対して単調非減少である**（後述）

#### 既定値（FR-03.5、担当者が変更可能）

```text
CostModel(bands=(
    CostBand(upper_bound_km=2.0,  rule=FLAT,   amount_yen=0.0),      # 徒歩
    CostBand(upper_bound_km=10.0, rule=FLAT,   amount_yen=300.0),    # 公共交通機関
    CostBand(upper_bound_km=None, rule=PER_KM, amount_yen=400.0),    # タクシー
))
```

#### 修正後の `TravelParameters`

| 属性 | 型 | 既定値 |
|------|----|--------|
| `detour_factor` | `float` | 1.3 |
| `average_speed_kmh` | `float` | 30.0 |
| `same_district_fixed_seconds` | `int` | 900 |
| **`cost_model`** | **`CostModel`** | **上記の既定値** |

## 3. 費用関数の単調非減少性 — 帯の設定が生む罠

**距離帯モデルは、設定次第で「遠くへ行くほど安くなる」費用関数を作れてしまう。**

### 3.1 具体例

```text
帯 2: 2 km 以上 10 km 未満、FLAT 300 円
帯 3: 10 km 以上、       PER_KM 20 円/km
```

| 距離 | 費用 |
|------|------|
| 9.9 km | 300 円 |
| **10.0 km** | **200 円** ← **安くなる** |

### 3.2 なぜ致命的か

最適化は総移動費用を最小化する。上記の設定では、**9.9 km の施設より 10.0 km の施設へ派遣するほうが「費用が安い」**と判定される。

**最適化が、より遠い施設へ職員を送ることを選ぶ。** これは本プロジェクトの目的（移動時間と費用の削減）に真っ向から反する。

### 3.3 対策

`CostModel` の**生成時に単調非減少性を検証し、違反する設定を拒否する**（fail closed / SECURITY-15）。

検証方法は `business-rules.md` の BR-D04 に定める。

**この不変条件は、Application Design や NFR Design の段階では見えなかった。距離帯モデルを採用したことで初めて現れた。**

## 4. `DistanceCacheEntry`（U-02 が定義する唯一の型）

`P-03 DistanceCachePort` が扱うエントリ。

| 属性 | 型 | 説明 |
|------|----|------|
| `district_a` | `SchoolDistrictId` | **正規化後**の小さい方の ID |
| `district_b` | `SchoolDistrictId` | **正規化後**の大きい方の ID |
| `great_circle_km` | `float` | **大円距離のみ**（迂回係数を乗じる前） |

### 4.1 キーの正規化（申し送り U01-H1）

キーは常に `(min(id_1, id_2), max(id_1, id_2))` に正規化する。

**帰結**: `cached_distance(a, b)` と `cached_distance(b, a)` は**同一のエントリを引く**。返る値はビット単位で同一である。

**INV-07b（キャッシュ経由の対称性）が、丸め誤差の議論を経ずに、構造的に厳密となる。**

### 4.2 大円距離のみを保存する理由（Q3=A）

| 保存する値 | キャッシュ無効化の契機 |
|-----------|---------------------|
| **大円距離**（採用） | **小学校区マスタの更新時のみ** |
| 実移動距離（大円距離 × 迂回係数） | 小学校区マスタの更新時 **および迂回係数の変更時** |
| 移動時間・費用まで | 上記に加え、平均速度・費用モデルの変更時 |

迂回係数・平均速度・費用モデルは、担当者が画面から変更できる（US-14）。**これらの変更でキャッシュが無効になると、変更のたびに最大 1 万要素の再計算が走る。**

大円距離は小学校区の代表点座標のみに依存する。座標が変わらない限り、キャッシュは有効である。

### 4.3 キャッシュのサイズ

小学校区数を `D` とすると、正規化により **`D(D+1)/2` エントリ**（対角成分を含む）。

| `D` | エントリ数 |
|-----|----------|
| 50 | 1,275 |
| 100 | 5,050 |
| 200 | 20,100 |

NFR-P03 が想定していた 40 万要素（職員 2,000 × 施設 200）より **1〜2 桁小さい**。距離が職員・施設ではなく**小学校区の組**でのみ決まるためである。
