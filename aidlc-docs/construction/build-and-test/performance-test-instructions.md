# Performance Test Instructions

## 位置づけ

PoC は稼働率目標（SLA）を定めず、水平スケールも行わない（NFR Requirements Q10=A、shared-infrastructure.md）。したがって本ステージの性能テストは**限定的・任意**とし、要件に直結する 1 点（最適化計算時間）にのみ焦点を当てる。

## 性能要件（該当分）

| 項目 | 要件 | 根拠 |
|------|------|------|
| 最適化計算時間 | 制限時間（既定 300 秒、`time_limit_seconds`）内に打ち切り、その時点の最良解を返す | NFR-P02、US-20 |
| API 応答性 | 300 秒の求解中も API プロセスは応答を保つ | プロセス分離（U07-H13） |
| ポーリング負荷 | 約 2 秒間隔、終端で停止 | NFR-FE-P2、PAT-FE-02 |
| フロント初期表示 | 小さなバンドル（JS 約 231 KB / gzip 73 KB） | NFR-FE-P1/P4 |

## テスト観点と方法

### 1. 求解の時間打ち切り（最重要）
- **確認済みの設計**: CP-SAT に `time_limit_seconds` を渡し、超過時は最良解 + 最適性ギャップを返す（U-04）。求解はワーカーの**トランザクション外**で実行（U07-H13）→ API を阻害しない。
- **手動計測（任意）**: 大きめの問題（施設×職員）を投入し、`time_limit_seconds` を小さく設定 → 実測打ち切り時間が制限時間内かを確認。求解中に別リクエスト（例: `GET /health`）が即応することを確認。

### 2. API 応答性（求解中）
```bash
# ワーカーが 300 秒級ジョブを処理中に、API プロセスが応答するか
# 別ターミナルで:
time curl -s http://localhost:8000/health   # 即応（ミリ秒オーダ）を確認
```

### 3. 負荷試験（任意・PoC では非必須）
- 数名規模の同時利用（NFR-FE-S1）を超える負荷試験は PoC スコープ外。
- 実施する場合は k6/Locust 等で `POST /optimizations` の受理レイテンシと `GET /optimizations/{id}` のポーリング負荷を計測。

## 結果（PoC）

- **バンドルサイズ**: 実測 JS 231.07 KB（gzip 73.37 KB）、CSS 1.70 KB。要件「過大な UI キットを避ける」を満たす。
- **プロセス分離**: claim（短 tx）→ 求解（tx 外）→ 保存（短 tx）を `test_stateful.py`/`worker.py` で担保。SQLite 単一ライタのストールを回避。
- **負荷/ストレス試験**: PoC では未実施（スコープ外、SLA なし）。実運用移行時に実施する申し送りとする。

## 最適化が要件を満たさない場合

1. `time_limit_seconds` / 目的関数の重みを調整（US-17）。
2. 問題規模が NFR-P02（40 万バイナリ変数）に迫る場合はソルバーパラメータ・距離バンドモデルを見直す（U-04）。
