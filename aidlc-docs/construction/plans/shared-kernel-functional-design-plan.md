## 2. 本ステージで解決すべき論点

### 論点 1: 浮動小数点の対称性と INV-07（最重要）

`INV-07` は「距離関数は対称である: `distance(a, b) == distance(b, a)`」と定めている。

しかし Haversine 距離を**浮動小数点**で計算する場合、実装によっては引数の順序で丸め誤差が変わり、**厳密な等価が成立しないことがある**。プロパティベーステストで厳密等価（`==`）を要求すると、テストが失敗しうる。

PBT-02 は「損失のある変換は許容偏差を文書化し、その許容範囲内でテストする」ことを求めている。**許容誤差を定義するか、実装で対称性を保証するか**を決める必要がある。

→ **Question 3, Question 4 で確認する。**

### 論点 2: 移動費用の型と丸め

移動費用は円建てである。円未満の端数をどこで、どのように処理するかを定めないと、`totalTravelCost`（総移動費用）の集計結果が実装依存になる。

また、目的関数は「総移動時間・総移動費用・不公平性の重み付き和」であり、費用が整数か実数かで最適化の定式化が変わる。

→ **Question 5 で確認する。**

### 論点 3: 識別子の体系

職員 ID、施設 ID、小学校区 ID は、既存の業務システムから引き継ぐ自然キーか、本システムが採番するサロゲートキーか。CSV インポート（US-07〜US-09, US-11）の設計に影響する。

→ **Question 1 で確認する。**

### Question 1: 識別子の体系（Domain Model）

職員 ID、施設 ID、小学校区 ID をどう扱いますか？

A) **すべて自然キー（既存システムの ID をそのまま使う）** — 職員 ID は人事システムの職員番号、施設 ID は避難所の管理番号、小学校区 ID は行政の校区コード。CSV に含まれる ID をそのまま主キーとする **（推奨。CSV インポートが単純になり、外部システムとの突合も容易）**

B) **すべてサロゲートキー（本システムが採番）** — 自然キーは別の属性として保持する。ID の体系変更に強いが、CSV インポート時に自然キー → サロゲートキーの解決が必要

C) **職員 ID のみ自然キー、他はサロゲートキー**

### Question 3: 距離・移動時間の数値型（Domain Model / Business Rules）

**論点 1 への対応です。**

`INV-07`（距離の対称性）を、プロパティベーステストでどう検証しますか？

A) **浮動小数点を使い、許容誤差を定義する** — `|distance(a,b) - distance(b,a)| < ε`（例: ε = 1e-9 km）を不変条件とする。PBT-02 の「損失のある変換は許容偏差を文書化する」に従う **（推奨。実装が単純で、地理計算の標準的な扱い）**

B) **浮動小数点を使い、実装で厳密な対称性を保証する** — 入力座標を正規化（例: 常に緯度の小さい方を第 1 引数にする）してから計算することで、`distance(a,b) == distance(b,a)` を厳密に成立させる。テストは厳密等価で書ける

C) **固定小数点（メートル単位の整数）を使う** — 丸めを 1 か所に集約し、厳密等価を成立させる。ただし迂回係数の乗算で再び丸めが発生する

X) Other（`[Answer]:` の後に自由に記述してください）

[Answer]: A

### Question 4: 移動時間の粒度（Domain Model / Business Rules）

移動時間を職員に提示する際、どの粒度で扱いますか？

A) **実数の分（`float minutes`）** — 内部計算は実数で保持し、表示時のみ丸める。集計（総移動時間）の誤差が最小

B) **整数の分（`int minutes`）** — 各職員の移動時間を分単位に丸めて保持する。人間が理解しやすいが、丸めが 2,000 回累積すると総移動時間に最大 1,000 分（約 17 時間）の誤差が生じうる

C) **秒単位の整数（`int seconds`）** — 丸め誤差が実質無視できる。表示時に分へ変換する **（推奨。集計誤差を避けつつ、整数の厳密性を得られる）**

X) Other（`[Answer]:` の後に自由に記述してください）

[Answer]: C

### Question 5: 移動費用の型と丸め（Domain Model / Business Rules）

**論点 2 への対応です。**

移動費用は「実移動距離 × 距離単価（円/km）」で算出します（FR-03.5、A-04）。

A) **円未満を切り上げて整数円で保持する** — 各職員の費用を整数円に丸めてから集計する。実際の支給額に近いが、丸めが累積する

B) **内部は実数のまま保持し、表示・エクスポート時のみ整数円に丸める** — 総移動費用の集計誤差が最小。目的関数も実数で扱える **（推奨）**

C) **銭単位の整数（1 円 = 100 銭）で保持する** — 厳密な整数演算だが、実務上の意味が薄い

X) Other（`[Answer]:` の後に自由に記述してください）

[Answer]: B

### Question 12: 不公平性の指標の定義（Business Rules）

**この決定は U-04 optimization-engine の目的関数に影響しますが、値オブジェクト `ObjectiveWeights` が U-01 に属するため、ここで確認します。**

FR-04.2 は目的関数の第 3 項を「不公平性の指標（最大移動時間、または移動時間の分散）」と定めています。どちらを採用しますか？

A) **最大移動時間の最小化（ミニマックス）** — 「最も遠くへ行かされる職員の移動時間」を最小化する。線形計画法で表現でき、MILP ソルバーで扱いやすい **（推奨。計算効率が良く、職員にとって説明しやすい）**

B) **移動時間の分散の最小化** — 負担のばらつきを均す。二次計画問題になり、MILP ソルバーでは扱えない（線形近似が必要）

C) **両方を実装し、担当者が選択できる** — 実装コストが増える
