# ビジネスルール — U-07 `api-orchestration`

**作成日**: 2026-07-17
**ステージ**: CONSTRUCTION - Functional Design（ユニット 7 / 8）

---

## 1. API 境界のルール

### BR-API01: Pydantic は U-07 に閉じ込める（Q1=A, U-01 パターン 1）
Pydantic の DTO は U-07 のみに存在する。ドメイン層（U-01）とその利用ユニット（U-02〜U-06）は Pydantic を知らない。リンタ契約が既にこれを強制している。

### BR-API02: ドメイン型を直接シリアライズしない（Q1=A, NFR-M05）
受信・送信ともに **DTO ↔ ドメイン型の明示的な変換**を経る。ドメイン型を直接 JSON にすると、内部構造が API 契約になり、ドメインの変更が API を壊す。

### BR-API03: 明示的な API 境界（NFR-M05, H-5）
フロントエンドとバックエンドは、同一ホストで稼働していても**プロセス内の直接呼び出しで結合しない**。境界は HTTP。バックエンドの URL は設定として外部化する（実運用のオンプレミス分離をコード変更なしに行うため）。

## 2. ミドルウェアと応答のルール

### BR-API04: ミドルウェアの順序（U06-H4, Q3=A）
**SEC-03 IP → SEC-04 レート制限 → SEC-01 認証 → SEC-02 認可 → SEC-05 入力検証**。安価で広範な拒否を先に置く。

### BR-API05: deny by default（SECURITY-08, US-01）
未認証・非許可 IP・レート超過・認可拒否の要求は、**業務ロジックに到達しない**。

### BR-API06: 汎用応答（SECURITY-09, U01-H14）
エラー応答に**スタックトレース・内部パス・フレームワークバージョンを含めない**。認証失敗は利用者の存在を漏らさない汎用メッセージ。詳細は構造化ログ（PII なし）へ。

### BR-API07: 予期しない例外は 500 + 汎用（SECURITY-15, fail closed）
ハンドラが把握していない例外は、握り潰さず **500 + 汎用メッセージ**とする。「原因不明なので通す」分岐を作らない。

### BR-API08: セキュリティヘッダ（SECURITY-04）
すべての応答に CSP, HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy を付与する。

### BR-API09: CSV インポートエラーは行番号付きで全件返す（BR-DM02）
`CsvImportError` は 400 + **全エラーを行番号付き**で返す。**個人情報を含めない**（BR-DM14）。

## 3. 合成ルートと注入のルール

### BR-API10: 単一の合成ルート（Q2=A）
全ユニットの組み立てを 1 箇所で明示的に行う。DI コンテナライブラリを導入しない。

### BR-API11: `SessionStorePort` の実装は U-07 が持ち、U-06 に注入する（U06-H2）
U-06 は `sqlalchemy` を import できない（契約で強制）。セッションの DB 永続化は U-07 の `SqlSessionStore` が担い、U-06 に注入される。

### BR-API12: `sanitize_csv_cell` を CSV 出力に注入する（U06-H3, MU-02）
U-03 `serialize_csv` / U-05 `export_report_csv` の注入口に、U-06 の `sanitize_csv_cell` を**必ず**渡す。**渡し忘れると MU-02 の対策が無効**になるため、合成ルートで一元的に注入し、テストで検証する（P-API07）。

## 4. 非同期ジョブのルール

### BR-API13: 最適化はジョブとして実行する（NFR-P02, Q4=A）
`POST /optimizations` は**即座に 202 + `job_id`** を返す。求解（最大 300 秒）は**ワーカープロセス**で実行し、API をブロックしない。

### BR-API14: ジョブ状態（Q4=A）
`QUEUED → RUNNING → {SUCCEEDED, INFEASIBLE, FAILED}`。終端状態から遷移しない。

### BR-API15: `INFEASIBLE` は `FAILED` ではない
実行不可能は**担当者が行動すべき状態**（追加申告、条件見直し）であってシステム障害ではない。U-04 の `InfeasibilityDiagnosis` をそのまま提示する。

### BR-API16: 単一ワーカー（A-07）
ジョブの取得は単一ワーカー前提。複数ワーカーでの競合制御は本 PoC の対象外（実運用で必要なら排他制御を追加）。

---

## 5. 再最適化と手動修正のルール

### BR-API17: 再最適化モードの選択（FR-06.6, US-24, Q5=A）
**FULL**（前回破棄・最適・内示済みの割当が変わりうる）と **INCREMENTAL**（前回をピン留め・既存不変・全体最適でない）を担当者が選ぶ。**トレードオフを明示**する。

### BR-API18: ピン留め違反は再最適化しない（FR-06.4）
ピン留めがハード制約に違反する場合、U-04 は solve せずエラーを返す。U-07 は 400 + 該当制約（施設/部署 ID、PII なし）を返す。担当者はピン留めを解除して再実行する。

### BR-API19: 手動修正は U-04 の検証を呼ぶ（FR-06.3, Q6=A）
手動変更後のハード制約検証は、**U-04 の公開検証関数**を呼ぶ（U07-H1）。**U-07 で C1〜C5 を再実装しない**——制約の解釈が 2 ユニットに分かれると乖離する。U-04 が制約の唯一の権威。

### BR-API20: 手動修正を監査する（FR-07.1, US-03）
割当の作成・変更を、**誰が/いつ/何を/変更前後の施設 ID** で監査ログに記録する（U-06 の `AuditService`）。**PII を含めない**。

---

## 6. 認証・セッションのルール

### BR-API21: セッションは HttpOnly Cookie（Q7=A, SECURITY-06）
セッション ID は **HttpOnly + Secure + SameSite=Strict** の Cookie で受け渡す。**JavaScript から読めない**——XSS でセッションを盗まれる経路を塞ぐ。応答ボディに入れない。

### BR-API22: ログアウトは即時失効
`DELETE /sessions` は U-06 の `logout` を呼ぶ。不透明なサーバー側セッションのため即時に効く。

---

## 7. 個人情報のルール（SECURITY-03）

### BR-API23: エラー応答・ログに個人情報を含めない
応答 DTO に氏名を含めるのは**業務上必要な画面のみ**（職員一覧など）。**エラー応答・ログ・監査には含めない**（職員 ID のみ）。
