## 3. 本ステージで解決すべき設計上の緊張

### 緊張 1: Pydantic とヘキサゴナルアーキテクチャの衝突（最重要）

| 決定 | 内容 | 出典 |
|------|------|------|
| Application Design Q1=B | ヘキサゴナルアーキテクチャ。**ドメイン層は何にも依存しない**（フレームワークを含む） | `components.md` セクション 1.1 |
| NFR Requirements Q2=A | FastAPI + **Pydantic** による入力検証（SECURITY-05） | `tech-stack-decisions.md` 決定 2 |

`shared-kernel` のエンティティを Pydantic の `BaseModel` として実装すると、**ドメイン層が Pydantic（＝ Web フレームワーク由来のライブラリ）に依存する**。これはヘキサゴナルアーキテクチャの依存規則に反する。

一方、Pydantic を使わなければ、`U-07 api-orchestration` は API の入出力用に**別途 DTO を定義し、ドメイン型との変換を書く**必要がある。

→ **Question 1 で確認する。**

### 緊張 2: 値オブジェクトの不変性と、生成時バリデーションの実効性

BR-01〜BR-07 は「不正な値を持つオブジェクトは生成そのものを拒否する」と定める。しかし**オブジェクトが可変であれば、生成後に不正な値を代入できる**。

```text
c = Coordinates(latitude=35.0, longitude=139.0)   # 生成時に検証される
c.latitude = 999.0                                 # 可変なら、ここで不変条件が壊れる
```

生成時バリデーション（NFR-U01-R01）を実効あるものにするには、**値オブジェクトを不変にする必要がある**。

→ **Question 2 で確認する。**

### 緊張 3: 列挙値の表記（日本語 vs 英語識別子）

`tech-stack-decisions.md` 決定 8 は、列挙値を日本語で記した（`管理職`, `一般職`, `事務職` 等）。これらは **CSV の列値**として現れ、**API の JSON**にも現れ、**コード上の識別子**にもなる。

3 者を同一の文字列にするか、コード上は英語識別子とし、CSV/API では日本語にマッピングするかを決める必要がある。

→ **Question 3 で確認する。**

### Question 1: ドメイン型の実装パターン（Security Patterns / Logical Components）

**緊張 1 への対応です。本ステージで最も重要な決定です。**

A) **ドメイン層は標準ライブラリのみで実装し（`dataclass` + `__post_init__` によるバリデーション）、Pydantic は `U-07 api-orchestration` の API 境界にのみ用いる** — ヘキサゴナルアーキテクチャの依存規則を厳守する。U-07 が DTO ↔ ドメイン型の変換を担う。変換コードが増えるが、ドメイン層が純粋に保たれ、将来 Web フレームワークを差し替えても U-01 が影響を受けない **（推奨）**

B) **ドメイン層のエンティティを Pydantic の `BaseModel` として実装する** — バリデーションが宣言的に書け、DTO 変換が不要になる。ただし**ドメイン層が Pydantic に依存する**ため、Application Design Q1=B（ヘキサゴナル）の依存規則に反する。Pydantic の破壊的変更が全ユニットに波及する

C) **ドメイン層は `dataclass`、API 境界の DTO は Pydantic とし、変換を自動生成する** — A の変換コストを軽減する。ただし自動生成の仕組みが追加の複雑さを持ち込む

### Question 2: 値オブジェクトとエンティティの不変性（Security Patterns）

**緊張 2 への対応です。**

A) **値オブジェクトとエンティティをすべて不変（frozen）とする** — 生成後の属性代入を型レベルで禁止する。生成時バリデーション（BR-01〜BR-07）が実効的になる。変更が必要な場合は新しいインスタンスを生成する（`replace()`） **（推奨。不変条件が生成から破棄まで維持されることを構造的に保証できる）**

B) **値オブジェクトのみ不変とし、エンティティは可変とする** — エンティティは同一性（ID）で識別されるため、属性の変更は自然である。ただし `Coordinates` を持つ `SchoolDistrict` の座標を、生成後に不正な値へ書き換えられる余地が残る

C) **すべて可変とする** — 生成時バリデーションの実効性が失われる。BR-01〜BR-07 の意味が薄れる

X) Other（`[Answer]:` の後に自由に記述してください）

[Answer]: A

### Question 3: 列挙値の表記（Logical Components / Maintainability）

**緊張 3 への対応です。**

`Position` の値「管理職」は、コード上の識別子、CSV の列値、API の JSON 値の 3 か所に現れます。

A) **コード上は英語識別子（`MANAGER`, `GENERAL`）とし、CSV / API では日本語表記との相互変換を行う** — 変換表を 1 か所に集約する。コードが国際化に耐え、識別子として扱いやすい **（推奨）**

B) **すべて日本語文字列で統一する**（`Position.管理職`） — 変換が不要。ただし Python の識別子として日本語を使うことになり、ツールチェーン（linter, IDE）との相性に懸念がある

C) **コード上は英語識別子、CSV / API も英語識別子とし、日本語は UI の表示時のみ変換する** — バックエンドが完全に英語で統一される。ただし**担当者が作る CSV に英語識別子を書かせることになり、運用上の負担が大きい**

### Question 4: 識別子型の区別（Security Patterns / Maintainability）

`StaffId`, `FacilityId`, `SchoolDistrictId`, `DepartmentId`, `EventId` はいずれも文字列です。取り違えを防ぐ仕組みが必要です。

A) **`NewType` で区別する**（`StaffId = NewType("StaffId", str)`） — `mypy` が取り違えを検出する。実行時のオーバーヘッドがゼロ。文字列として扱える **（推奨。mypy strict モード（Q11=A）と組み合わせて機能する）**

B) **専用のクラスとして定義する** — 実行時にも型が区別される。ただしオーバーヘッドがあり、CSV / JSON との相互変換にコードが必要

C) **単なる `str` として扱う** — 取り違えを検出できない。`assignment.staffId` に施設 ID を渡してもエラーにならない

### Question 6: 個人情報を含む型のログ出力防止（Security Patterns / NFR-U01-R03）

`Staff` を誤って `print()` や `logger.info()` に渡すと、氏名と居住小学校区がログへ出力されます。構造的に防ぐ手段を確定してください。

A) **`Staff` の文字列表現（`__repr__` / `__str__`）をオーバーライドし、氏名と居住小学校区を伏字にする** — 例: `Staff(id=S001, name=<redacted>, residence=<redacted>)`。誤ってログに渡しても個人情報が出ない **（推奨。多層防御。SECURITY-11）**

B) **リンタ規則のみで防ぐ**（`src/security/` が `Staff` を import しないことを検証する） — U-06 からの流出は防げるが、他ユニットが誤って `Staff` をログに渡す経路は残る

C) **A と B の両方を実施する**

### Question 8: PBT のシード方針（Security Patterns / Reliability、PBT-08）

PBT-08 は「PBT はシードにより再現可能でなければならない。CI は固定シードを用いるか、実行ごとにシードをログ出力すること」と定めます。

A) **CI では実行ごとにランダムなシードを用い、失敗時にシードをログ出力する** — 実行のたびに新しい入力空間を探索でき、未知のバグを見つけやすい。失敗は記録されたシードで再現できる **（推奨。PBT の目的に適う）**

B) **CI では固定シードを用いる** — 実行が完全に決定的になるが、同じ入力しか試さないため、新しいバグを見つける能力が失われる
