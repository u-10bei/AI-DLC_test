## 2. 論点: 共有インフラを、いつ・どのユニットで設計するか

### 2.1 状況

`construction/infrastructure-design.md` Step 6 は、共有インフラがある場合 `aidlc-docs/construction/shared-infrastructure.md` の作成を求める。

**本システムのインフラは、すべて共有インフラである。** モノリス（Units Generation Q1=A）であり、単一サーバー（A-07）で稼働する。U-01〜U-07 が同一のプロセス・同一の DB・同一のファイルシステムを共有する。

### 2.2 未解決のインフラ関連の申し送り

| ID | 事項 | 出典 |
|----|------|------|
| **U01-H16** | 監査ログの追記専用ファイル（`chattr +a`）の配置、属性付与、**保持期間 90 日以上の管理**（アプリケーション外の特権プロセスが行う） | U-01 NFR Requirements |
| **U01-H17** | 保存時暗号化をファイルシステム / ディスクレベルで実現する手段の確定 | U-01 NFR Requirements |
| **H-6** | 既存の公開基盤が提供する統制範囲（TLS 終端、アクセスログ、WAF の有無）の確認。**SECURITY-02 の適合判定に必要** | Workflow Planning |
| **NFR-S10.1 / S10.2** | ログイン制限と庁内出口 IP の許可リスト。**SECURITY-07 の文書化された例外の代償統制** | 要件 v1.3 |

**これらは U-01 の Infrastructure Design で扱うことも、後続ユニットに委ねることもできる。**

### 2.3 選択肢の分析

| 案 | 内容 | 利点 | 欠点 |
|----|------|------|------|
| **案 1** | **U-01 の Infrastructure Design をスキップし、共有インフラは U-06 security で設計する** | U-01 に実体がないステージを走らせない。U-06 は監査ログ・暗号化・IP 許可リストの主担当であり、申し送りの多くを所有する | U-03（DB）の Infrastructure Design が U-06 より先に来る（依存順は U-03 → U-04 → U-05 → U-06）。DB のインフラ設計時に、暗号化の方針が未確定になる |
| **案 2** | **U-01 の Infrastructure Design で `shared-infrastructure.md` を作成し、バックエンド全体のインフラを先に確定する** | U-01 は既にバックエンド全体の技術スタックを決定している。同じ論理でインフラも先に確定すれば、U-02〜U-07 は「共有インフラを参照する」だけで済む。SECURITY-01（暗号化）と SECURITY-14（監査ログ）の統制が最初に確定する | U-01 自身にはインフラがないため、ステージの名目と内容がずれる |
| **案 3** | **U-01 の Infrastructure Design をスキップし、共有インフラは U-03 data-management で設計する** | U-03 が最初に実インフラ（DB、ファイルシステム）に触れるユニットである | U-03 はセキュリティ統制（IP 許可リスト、監査ログ）の主担当ではない |

### 2.4 分析

**依存順は U-01 → U-02 → U-03 → U-04 → U-05 → U-06 → U-07 である。**

実インフラに最初に触れるのは **U-03 data-management**（DB、距離キャッシュの永続化）である。しかし U-03 の時点で以下が未確定だと、設計が宙に浮く。

- SQLite ファイルをどこに置くか（暗号化ボリューム上か）→ **U01-H17**
- 監査ログのファイルをどこに置くか → **U01-H16**（U-03 は監査を呼び出す）

**したがって、共有インフラは U-03 より前に確定していることが望ましい。** U-01 と U-02 のうち、U-02 distance-cost も純粋関数のみでインフラを持たない。

**案 2 が、依存順と整合する唯一の選択肢である。**

なお、案 2 を採る場合も **U-01 固有のインフラ設計は存在しない**。作成するのは `shared-infrastructure.md`（バックエンド全体）であり、`{unit-name}/infrastructure-design/` 配下には「U-01 にインフラ表出がないこと」の記録のみを置く。

### Question 1: 共有インフラの設計をどこで行うか（Shared Infrastructure）

**本ステージで唯一の論点です。**

セクション 2.4 の分析のとおり、実インフラに最初に触れるのは U-03 data-management です。しかし U-03 の設計には、暗号化ボリュームの方針（U01-H17）と監査ログファイルの配置（U01-H16）が先に確定している必要があります。

A) **U-01 の Infrastructure Design で `shared-infrastructure.md` を作成し、バックエンド全体のインフラを先に確定する** — U-01 が既にバックエンド全体の技術スタックを決定したのと同じ論理。U-02〜U-07 は共有インフラを参照するだけで済む。U-01 固有のインフラ設計は「存在しない」と記録する **（推奨。依存順と整合する唯一の案）**

B) **U-01 の Infrastructure Design をスキップし、共有インフラは U-06 security で設計する** — U-06 は監査ログ・暗号化・IP 許可リストの主担当。ただし U-03（DB）の設計が U-06 より先に来るため、その時点で暗号化と監査ログの方針が未確定になる

C) **U-01 の Infrastructure Design をスキップし、共有インフラは U-03 data-management で設計する** — U-03 が最初に実インフラに触れる。ただし U-03 はセキュリティ統制の主担当ではない

D) **U-01 の Infrastructure Design を完全にスキップし、共有インフラの設計時期は後で決める** — 決定を先送りする

### Question 3: 既存の公開基盤が提供する統制範囲（申し送り H-6、Networking / Monitoring）

**Question 1 で A を選択した場合、本ステージで扱います。** それ以外を選択した場合は、該当ユニットへ持ち越します。

要件 A-06 により、庁内サーバーをインターネットから到達可能にする仕組みは既に存在します。**この基盤が何を提供するかが、SECURITY-02（ネットワーク中継機器のアクセスログ）の適合判定に必要です。**

### Question 4: 保存時暗号化の具体的手段（申し送り U01-H17、Storage）

**Question 1 で A を選択した場合、本ステージで扱います。**

NFR Requirements の Follow-up Q3=A により、保存時暗号化はファイルシステム / ディスクレベルで実現します。SQLite ファイル、監査ログファイル、距離キャッシュのすべてが対象です。

A) **暗号化されたボリューム上にアプリケーションのデータディレクトリを配置する**（Linux なら LUKS、クラウドなら暗号化ディスク） — 具体的な手段は運用環境に委ね、要件として「データディレクトリは暗号化ボリューム上にあること」を定める **（推奨）**

B) **具体的な暗号化手段をここで確定する** — 手段を `[Answer]:` の後に記述してください

C) **PoC では仮名化データのみを扱うため、暗号化を見送る** — **SECURITY-01 のブロッキング所見になります。** 居住小学校区は仮名化されずに残るため、個人の特定可能性は完全には消えません

### Question 5: 監査ログの保持期間管理（申し送り U01-H16、Storage / Monitoring）

**Question 1 で A を選択した場合、本ステージで扱います。**

SECURITY-14 は監査ログの **90 日以上の保持**を要求します。一方、追記専用ファイル（`chattr +a`）は**アプリケーションからローテーション・削除ができません**。保持期間の管理は、アプリケーション外の特権プロセスが行う必要があります。

A) **cron 等の特権プロセスが、日次でファイルをローテーションする。90 日を超えた古いファイルのみを削除する。ローテーション後のファイルにも `chattr +a` を再付与する** **（推奨）**

B) **ローテーションを行わず、単一のファイルに永続的に追記し続ける** — 90 日の保持は満たすが、ファイルが際限なく増大する

C) **保持期間の管理を実運用時に先送りする** — SECURITY-14 の例外として文書化する必要があります
