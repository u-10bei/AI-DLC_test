# User Stories Assessment

**作成日**: 2026-07-09
**ステージ**: INCEPTION - User Stories - Part 1 (Planning) - Step 1

---

## Request Analysis

- **Original Request**: 災害時避難所応援職員の割当を、職場単位から居住地考慮型の数理最適化に置き換える PoC の構築
- **User Impact**: Direct（割当担当者が直接操作する Web アプリケーション。割当結果は全職員の実際の派遣先を決定する）
- **Complexity Level**: Complex
- **Stakeholders**:
  - 割当業務を担当する事務職員（危機管理担当課、選挙管理委員会事務局を想定）
  - 割当される職員（本 PoC の直接利用者ではないが、成果の受益者）
  - 上長・関係部署（削減効果の提示を受ける立場、SC-01）
  - 組織のセキュリティ担当部署（NFR-S10 の統制に関与）

---

## Assessment Criteria Met

### High Priority（該当するものは必ず実施）

- [x] **New User Features**: 割当最適化、比較レポート、手動調整はいずれも新規のユーザー向け機能である（FR-04, FR-05, FR-06）
- [x] **User Experience Changes**: 現行の職場単位割当という業務プロセス自体を変更する。担当者の作業手順が根本的に変わる
- [x] **Complex Business Logic**: ハード制約 5 件（C1〜C5）とソフト制約 1 件（S1）、3 項からなる重み付き目的関数、実行不可能時のハンドリング（FR-04.5）など、複数のシナリオと業務ルールを含む
- [ ] **Multi-Persona Systems**: 本 PoC の直接利用者は割当担当者に限定される（CQ4=A により全職員向け機能は次フェーズ）。ただし間接的な受益者として「割当される職員」が存在し、その負担軽減が目的関数そのものであるため、ペルソナとして定義する価値がある
- [ ] **Customer-Facing APIs**: 該当しない（外部システムからの利用は想定外）
- [ ] **Cross-Team Projects**: 部分的に該当（危機管理部門、人事部門、情報システム部門にまたがる）

### Medium Priority（複雑性に基づき判断）

- [x] **Security Enhancements**: 認証・認可（NFR-S04, NFR-S05, NFR-S10.1）がユーザーの操作に直接影響する
- [x] **Data Changes**: 職員の個人情報（居住小学校区）を新たに業務データとして扱う

### Complexity Assessment Factors

- [x] **Scope**: イベント管理、マスタ管理、距離算出、最適化、比較レポート、手動調整という複数のコンポーネント／ユーザータッチポイントにまたがる
- [x] **Ambiguity**: 手動調整と再最適化の相互作用（FR-06.4 のピン留め）、実行不可能時の担当者の行動（FR-04.5）など、ストーリーで明確化すべき領域が残る
- [x] **Risk**: 割当結果は職員の実際の派遣先を決定する。誤った割当は災害対応の遅延に直結し、業務上のインパクトが大きい
- [x] **Stakeholders**: 複数の業務ステークホルダーが関与する
- [x] **Testing**: ユーザー受入テストが必要。加えて PBT 拡張（NFR-T01〜T08）が有効であり、受入基準を不変条件として形式化できる
- [x] **Options**: 最適化の解法（厳密解法 vs 発見的解法）、手動調整の実現方式など、複数の妥当な実装アプローチが存在する

### Skip Criteria（いずれも該当しない）

- [ ] Pure Refactoring — 該当しない（新規構築）
- [ ] Isolated Bug Fixes — 該当しない
- [ ] Infrastructure Only — 該当しない
- [ ] Developer Tooling — 該当しない
- [ ] Documentation — 該当しない

## Decision

**Execute User Stories**: **Yes**

**Reasoning**:

High Priority 指標のうち 3 件（New User Features、User Experience Changes、Complex Business Logic）に明確に該当する。ルールの規定により、High Priority 指標に該当する場合は User Stories を必ず実施する。

加えて、Complexity Assessment Factors の 6 項目すべてに該当しており、Medium Priority の判断基準からも実施が支持される。Skip Criteria にはひとつも該当しない。

本プロジェクトに固有の実施理由は以下の 2 点である。

1. **受入基準がプロパティベーステストの不変条件に直結する**。PBT 拡張が有効（NFR-T01〜T08）であり、requirements.md セクション 4.3 で 9 件の不変条件を既に特定している。User Stories の受入基準を明示的に定義することで、これらを Functional Design での PBT-01（プロパティ特定）へ直接引き渡せる。

2. **「割当される職員」という間接的ペルソナが目的関数そのものである**。本 PoC の直接利用者は割当担当者のみだが、最適化が最小化するのは「割当される職員の移動時間・費用」である。このペルソナを明示的に定義しないと、目的関数の重み調整（FR-04.2）が誰の何を改善するのかが不明瞭になる。

## Expected Outcomes

- **要件の明確化**: 手動調整とピン留め再最適化の相互作用（FR-06.3, FR-06.4）、および最適化が実行不可能な場合の担当者の行動（FR-04.5）を、ストーリーと受入基準として具体化する
- **テスト基準の確立**: 各ストーリーの受入基準が、例示ベーステスト（PBT-10）とプロパティベーステスト（PBT-03）の双方の入力となる
- **ステークホルダー間の合意形成**: 危機管理部門・人事部門・情報システム部門にまたがる共通理解を確立する
- **実装リスクの低減**: 複数の妥当な実装アプローチが存在する領域（最適化の解法、手動調整の方式）について、ユーザー価値の観点から選択基準を明示する
- **目的関数の妥当性検証**: 「割当される職員」ペルソナを定義することで、重み調整機能（FR-04.2）が誰のどの負担を軽減するのかを追跡可能にする
