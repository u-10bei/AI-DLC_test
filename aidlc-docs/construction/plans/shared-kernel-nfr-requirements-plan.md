## 3. 技術スタックの選択肢と分析

### 3.1 言語の比較（最重要の決定）

**選定基準の優先順位**:
1. **MILP ソルバーの利用可能性**（NFR-P02。この要件を満たせない言語は失格）
2. **PBT フレームワークの成熟度**（PBT-09 がブロッキング制約であるため）
3. Web フレームワーク、DB ドライバ、CSV 処理の成熟度
4. 庁内での保守可能性

| 言語 | MILP ソルバー | PBT フレームワーク | Web | 評価 |
|------|-------------|------------------|-----|------|
| **Python** | **OR-Tools（CP-SAT / SCIP）、PuLP、Pyomo、python-mip**。選択肢が最も豊富。NFR-M01 の差し替えが容易 | **Hypothesis**。成熟度・シュリンキング品質ともに最高水準。ステートフルテストも対応 | FastAPI, Django, Flask | **最適** |
| **Java** | OR-Tools（Java バインディング）、OptaPlanner | jqwik（JUnit 5 統合、ステートフルテスト対応） | Spring Boot | 良好 |
| **TypeScript / Node.js** | 選択肢が乏しい。javascript-lp-solver は小規模問題向け。**40 万変数は現実的でない** | fast-check | Express, NestJS | **NFR-P02 を満たせない可能性が高い** |
| **Go** | 選択肢が乏しい。gonum に MILP なし | rapid | net/http, Echo | **NFR-P02 を満たせない可能性が高い** |

**分析**: 40 万の 0-1 変数を扱う MILP ソルバーが実質的に Python と Java に限られる。両者のうち、**Hypothesis の PBT 品質**と**数理最適化エコシステムの厚み**で Python が優位である。

**Python の性能への懸念について**: 最適化計算の実体は OR-Tools の C++ コアが実行する。Python はモデル構築とソルバー呼び出しのみを担う。距離行列の事前計算（最大 1 万要素、Q4=A のキャッシュ圧縮後）も NumPy でベクトル化できる。**NFR-P02 のボトルネックは言語ではなくソルバーである。**

### 3.2 非同期ジョブ基盤の比較

Q2=B により、最適化は非同期ジョブ + ポーリングで実行する。最大 300 秒を要する。

| 方式 | 追加の依存 | PoC 適合性 |
|------|----------|-----------|
| **DB バックエンドのジョブキュー**（ジョブ状態を業務 DB のテーブルに保持し、ワーカープロセスがポーリング） | **なし**（PostgreSQL のみ） | **単一サーバー（A-07）に適する。運用対象が増えない** |
| **Celery + Redis** | Redis | 分散環境向け。PoC には過剰 |
| **プロセス内スレッド / `asyncio` タスク** | なし | プロセス再起動でジョブが失われる。ジョブ状態を永続化できない |

### 衝突 1: SECURITY-14（監査ログの改竄防止）の実現手段が失われる（最重要）

Application Design の Question 6 で **A**（業務 DB とは別のストレージに追記専用で書き込み、**アプリケーションのアカウントに削除権限を与えない**）を選択されました。

PostgreSQL であれば、ロールと権限（`REVOKE DELETE, UPDATE`）でこれを強制できます。

しかし **SQLite にはユーザーもロールも存在しません**。ファイルを開ける者は、そのファイル内のあらゆるテーブルを `DELETE` も `DROP` もできます。**「アプリケーションのアカウントに削除権限を与えない」という統制は、SQLite 上では実現できません。**

このまま進めると、SECURITY-14 は**ブロッキング所見**になります。別の手段が必要です。

#### Follow-up Question 1
PoC における監査ログの改竄防止を、どう実現しますか？

A) **OS レベルの追記専用ファイルに書き込む** — 監査ログを JSON Lines 形式のファイルに追記し、Linux の `chattr +a`（append-only 属性）を付与する。この属性が付いたファイルは、root 以外は**追記のみ可能で、既存行の変更・削除・ファイルの削除ができない**。アプリケーションプロセスは追記だけできる。SQLite でも PostgreSQL でも同じ仕組みが使える **（推奨。`AuditLogPort` が削除メソッドを定義しないという設計とも整合する）**

B) **PoC でも監査ログ専用に PostgreSQL を使う** — 業務 DB は SQLite、監査ログは PostgreSQL。2 つの DB を運用することになる

C) **PoC では改竄防止を実施せず、SECURITY-14 の例外として文書化する** — 実運用時に PostgreSQL の権限分離で対応する。**この選択には、例外の明示的な了承が必要です**

### 衝突 2: 非同期ジョブ基盤（Q5=A）が SQLite 上で成立するか

Q5=A（DB バックエンドのジョブキュー）を選択されました。私はこれを PostgreSQL のテーブルとして説明していました。

SQLite では、**Web プロセス（FastAPI）とジョブワーカープロセスが同一ファイルに書き込みます**。SQLite は書き込みを直列化するため、既定の設定（ロールバックジャーナル、`busy_timeout = 0`）では、一方の書き込みトランザクションが他方をブロックし、API リクエストが `database is locked` で失敗しえます。

**成立させる条件**:
- WAL モード（`PRAGMA journal_mode = WAL`）を有効にする — 読み取りと書き込みが並行できる
- `PRAGMA busy_timeout` を設定する（例: 5000 ms）
- **最適化計算中に書き込みトランザクションを保持しない** — これは Application Design で既に定めています（「最適化の計算はトランザクション外で実行する」）

#### Follow-up Question 2
上記の条件のもとで、DB バックエンドのジョブキュー（Q5=A）を SQLite 上で採用しますか？

A) **採用する。WAL モードと `busy_timeout` を必須設定として記録する** — 単一サーバー（A-07）、単一ワーカーの構成であり、書き込み競合は限定的である **（推奨）**

B) **PoC ではジョブ状態をプロセス内メモリに保持する（Q5=C に変更）** — プロセス再起動でジョブが失われる。US-20（進捗のポーリング）が脆くなる

C) **PoC でも Redis を導入する（Q5=B に変更）** — 運用対象が増える

X) Other（`[Answer]:` の後に自由に記述してください）

### 衝突 3: SECURITY-01（保存時の暗号化）に DB 内の答えがない

SECURITY-01 は「すべてのデータ永続化ストアで、保存時の暗号化を有効にすること」を要求します。本システムは職員の氏名・居住小学校区（個人情報）を保存します。

PostgreSQL にはクラスタレベル・カラムレベルの選択肢がありますが、**SQLite の標準ビルドには暗号化機能がありません**（SQLCipher は別ビルドの拡張です）。

#### Follow-up Question 3
PoC における保存時の暗号化を、どう実現しますか？

A) **ファイルシステムまたはディスクレベルの暗号化で対応する** — SQLite ファイルを暗号化されたボリューム（LUKS、BitLocker、クラウドの暗号化ディスクなど）に配置する。統制の実装は Infrastructure Design ステージで具体化する **（推奨。DB 製品に依存せず、実運用の PostgreSQL でもそのまま通用する）**

B) **SQLCipher を採用する** — SQLite の暗号化ビルド。追加の依存とビルド手順が増える

C) **PoC では仮名化データのみを扱うため、保存時暗号化を SECURITY-01 の例外として文書化する** — 氏名は職員 ID に置換済み（CQ7=B）。ただし**居住小学校区は仮名化されず残る**ため、個人の特定可能性は完全には消えません

[Answer]: A

### 補足確認: PoC から実運用への DB 移行

SQLite → PostgreSQL の移行を安価に保つには、永続化アダプタ（`A-02 PersistenceAdapter`、U-03 に所属）が SQLite 固有の挙動に依存しないことが必要です。

#### Follow-up Question 4
DB 移行を見据えた実装方針を確定してください。

A) **データベース抽象化層（SQLAlchemy Core / ORM）とマイグレーションツール（Alembic）を採用し、SQLite 固有の SQL を使わない。SQLite の動的型付けに依存しない** — 移行は接続文字列の変更とマイグレーション再適用で済む **（推奨）**

B) **SQLite 用の SQL を直接記述し、移行時に書き直す** — PoC は速いが、移行時に U-03 の全面書き直しが必要
