**作成日**: 2026-07-09

**参照**: `requirements.md` v1.3, `personas.md`, `story-generation-plan.md`

## 構成方針

- **分解アプローチ**: Hybrid（Q1=F）— エピックを骨格とし、各エピック内はユーザージャーニー順。横断的関心事（認証・認可・監査）は独立エピック E1 として切り出す
- **受入基準の形式**: Given-When-Then（Q3=A）
- **不変条件**: 各ストーリーの受入基準に「不変条件」セクションを設ける（Q4=A）。PBT-01 により Functional Design へ引き渡す
- **粒度**: 中程度（Q5=B）。全 26 ストーリー
- **非機能要件**: ユーザーに観測可能なもののみストーリー化（Q6=A）
- **優先度**: MoSCoW（Q10=B）。**Must** = PoC の成功基準（SC-01, SC-02）に不可欠、**Should** = PoC の実用性に必要、**Could** = あれば有用、**Won't** = 本 PoC では実装しない

# 🔐 Epic 1: 認証・認可・監査（横断的関心事）

このエピックは全エピックに先行して満たされる必要がある。SECURITY-08、SECURITY-13、SECURITY-14 に対応する。

## US-01: 未認証アクセスの遮断

**MoSCoW**: Must
**ペルソナ**: P-02 システム管理者
**要件**: NFR-S10.1, NFR-S04, SECURITY-08

> **システム管理者** として、
> **未認証のリクエストが業務ロジックに一切到達しないこと** を望む。
> なぜなら **職員の個人情報（氏名、居住小学校区）を保護する必要がある** からだ。

### 受入基準

```gherkin
Scenario: 未認証ユーザーが保護されたエンドポイントにアクセスする
  Given ユーザーがログインしていない
  When 割当結果一覧のエンドポイントにアクセスする
  Then 401 Unauthorized が返る
  And 業務ロジックは実行されない
  And レスポンスにスタックトレースや内部パスが含まれない

Scenario: 公開エンドポイント以外はすべて認証を要求する（deny by default）
  Given システムに定義された全エンドポイントの一覧がある
  When 各エンドポイントを未認証で呼び出す
  Then 明示的に公開と指定されたエンドポイント（ログイン画面、ヘルスチェック）以外は
       すべて 401 Unauthorized を返す

Scenario: ログイン試行の総当たり攻撃を防ぐ
  Given ログインエンドポイントが存在する
  When 同一アカウントに対し規定回数を超える連続したログイン失敗が発生する
  Then そのアカウントは一時的にロックされる
  And ロック事象が監査ログに記録される
```

### 不変条件

- **新規**: 認証を要求しないエンドポイントの集合は、明示的に定義された公開エンドポイント集合と厳密に一致する（deny by default の形式的表現）

## US-02: 送信元 IP アドレスによるアクセス制限

**MoSCoW**: Must
**ペルソナ**: P-02 システム管理者
**要件**: NFR-S10.2, SECURITY-07（文書化された例外の代償統制）

> **システム管理者** として、
> **庁内イントラネットの出口グローバル IP アドレスからのアクセスのみを受け付けたい**。
> なぜなら **インターネット側に配置したサーバーへの到達可能範囲を庁内に限定する必要がある** からだ。

### 受入基準

```gherkin
Scenario: 許可リストに含まれる送信元からのアクセス
  Given 許可リストに庁内出口グローバル IP が登録されている
  When その IP アドレスからアクセスする
  Then リクエストは受理される

Scenario: 許可リストに含まれない送信元からのアクセス
  Given 許可リストに登録されていない IP アドレスがある
  When その IP アドレスからアクセスする
  Then リクエストは拒否される（403 Forbidden）
  And 業務ロジックは実行されない
  And 拒否事象が監査ログに記録される

Scenario: 許可リストは設定として外部化されている
  Given システムが稼働している
  When 許可リストを変更する
  Then コードの再ビルドなしに変更が反映される
```

## US-03: 割当結果変更の監査ログ記録

**MoSCoW**: Must
**ペルソナ**: P-02 システム管理者
**要件**: FR-07.1, SECURITY-13

> **システム管理者** として、
> **割当結果の作成・変更を、誰が・いつ・何を・変更前後の値とともに追跡したい**。
> なぜなら **割当結果は職員の実際の派遣先を決定するため、後から根拠を説明できる必要がある** からだ。

### 受入基準

```gherkin
Scenario: 割当結果の手動変更が監査ログに記録される
  Given 割当結果が確定している
  When 担当者が職員 S001 の割当先を施設 F010 から施設 F012 に変更する
  Then 監査ログに以下が記録される
    | 項目       | 値                    |
    | 実行者     | 担当者のアカウント ID |
    | 日時       | ISO 8601 形式         |
    | 対象       | 職員 S001             |
    | 変更前     | 施設 F010             |
    | 変更後     | 施設 F012             |

Scenario: 監査ログに個人情報が含まれない
  Given 監査ログが出力されている
  When ログの内容を検査する
  Then 職員の氏名、居住小学校区が含まれない
  And 職員 ID のみが記録されている
```

### 不変条件

- **新規**: 割当結果に対するあらゆる変更操作について、監査ログのエントリが 1 件以上生成される（変更操作数 ≤ 監査ログエントリ数）

---

## US-04: 監査ログの改竄防止

**MoSCoW**: Should
**ペルソナ**: P-02 システム管理者
**要件**: FR-07.3, SECURITY-14

> **システム管理者** として、
> **アプリケーションが自身の監査ログを削除・改変できないようにしたい**。
> なぜなら **監査ログが改竄可能であれば、追跡可能性が失われる** からだ。

### 受入基準

```gherkin
Scenario: アプリケーションから監査ログを削除できない
  Given 監査ログが追記専用ストレージに保管されている
  When アプリケーションが監査ログの削除を試みる
  Then 操作は失敗する

Scenario: 認証失敗と認可違反が記録される
  Given ユーザーが認可されていないリソースにアクセスを試みる
  When そのリクエストが拒否される
  Then 認可違反として監査ログに記録される
  And 設定された閾値を超えた場合にアラートが発報される
```

## US-05: イベントの登録

**MoSCoW**: Must
**ペルソナ**: P-01 割当担当者
**要件**: FR-01.1, FR-01.2

### 受入基準

```gherkin
Scenario: イベントを登録する
  Given 担当者がログインしている
  When 種別「災害時避難所応援」、名称「令和8年7月豪雨 避難所開設」、実施日「2026-07-15」を入力して登録する

  Given 担当者がログインしている
```

**MoSCoW**: Should
**ペルソナ**: P-01 割当担当者

## US-07: 職員マスタの CSV 一括インポート

**MoSCoW**: Must
**ペルソナ**: P-02 システム管理者
**要件**: FR-02.1, FR-02.5

> **システム管理者** として、
> **職員データ（500〜2,000 件）を CSV から一括で取り込みたい**。
> なぜなら **一件ずつ手入力することは運用上不可能であり、人事異動のたびに更新が必要になる** からだ。

### 受入基準

```gherkin
Scenario: 正常な CSV を取り込む
  Given 職員 ID、氏名、所属部署、職種、役職、保有資格、居住小学校区 の列を持つ CSV がある
  And 全行のデータが妥当である
  When 担当者がその CSV をインポートする
  Then 全件が職員マスタに登録される
  And 登録件数が表示される

Scenario: 不正な行を含む CSV を取り込む（fail closed）
  Given CSV の 15 行目に、存在しない小学校区 ID が指定されている
  When 担当者がその CSV をインポートする
  Then インポート全体がロールバックされ、1 件も登録されない
  And 15 行目のエラー内容が行番号とともに報告される

Scenario: 大規模データの処理時間
  Given 2,000 行の職員 CSV がある
  When インポートを実行する
  Then 30 秒以内に完了する
```

### 不変条件

- 参照: **INV-10**（CSV エクスポート → インポートのラウンドトリップ）
- **新規**: インポートが失敗した場合、データベースの状態はインポート前と完全に同一である（原子性）

## US-08: 施設マスタの CSV 一括インポート

**MoSCoW**: Must
**ペルソナ**: P-02 システム管理者
**要件**: FR-02.2, FR-02.5

> **システム管理者** として、
> **施設（避難所）データを CSV から一括で取り込みたい**。

## US-09: 小学校区マスタの CSV 一括インポート

**MoSCoW**: Must
**ペルソナ**: P-02 システム管理者
**要件**: FR-02.3, FR-03.1, A-02

# 📝 Epic 4: 従事可否申告の管理

**重要**: 本 PoC では、従事可否申告は**割当担当者が代理で CSV 一括登録**する。職員本人がシステムにログインして申告する機能は本 PoC の対象外である（A-08）。実運用では職員本人が入力する。

---

## US-11: 従事可否申告の CSV 一括登録

**MoSCoW**: Must
**ペルソナ**: P-01 割当担当者（実運用では P-03 従事職員）
**要件**: FR-02.7, FR-02.8, A-08

> **割当担当者** として、
> **職員から収集した従事可否申告を、イベント単位で CSV から一括登録したい**。
> なぜなら **従事可能と申告した職員のみが最適化の対象となるため、割当計算の前提となる** からだ。

### 受入基準

```gherkin
Scenario: 従事可否申告を一括登録する
  Given イベント E001 が登録されている
  And 職員 ID、従事可否、理由区分 の列を持つ CSV がある
  When 担当者がイベント E001 に対してその CSV をインポートする
  Then 各行が（職員 ID, イベント E001, 従事可否, 理由区分, 申告日時）として登録される

Scenario: 同一職員が複数イベントに異なる申告を行う
  Given 職員 S001 がイベント E001 に「従事可能」と申告している
  When 職員 S001 がイベント E002 に「従事不可（休暇）」と申告する
  Then 両方の申告が独立して保持される
  And イベント E001 の割当計算では S001 は対象となる
  And イベント E002 の割当計算では S001 は対象とならない

Scenario: 存在しない職員 ID を含む CSV
  Given CSV に職員マスタに存在しない職員 ID が含まれる
  When インポートを実行する
  Then バリデーションエラーとなり、インポート全体がロールバックされる
```

### 不変条件

- 参照: **INV-03**（従事不可と申告した職員は、いかなる施設にも割り当てられない）
- **新規**: 従事可否申告は（職員 ID, イベント ID）の組に対して定まる。同一組に対する複数の有効な申告は存在しない

## US-12: 追加の従事可否申告と申告履歴

**MoSCoW**: Must
**ペルソナ**: P-01 割当担当者
**要件**: FR-02.7, FR-04.5

> **割当担当者** として、
> **人員不足の調整後に取り付けた追加の従事可否申告を登録し、以前の申告を履歴として残したい**。
> なぜなら **「最初は従事不可だったが、調整の結果、従事可能になった」という経緯を追跡する必要がある** からだ。

### 受入基準

```gherkin
Scenario: 同一職員が同一イベントに再申告する
  Given 職員 S001 がイベント E001 に「従事不可（その他）」と申告している
  When 担当者が職員 S001 の申告を「従事可能」に更新する
  Then 最新の申告「従事可能」が有効となる
  And 以前の申告「従事不可（その他）」は履歴として保持される
  And 割当計算では S001 が対象となる
```

## US-27: 削減効果の比較レポート

**MoSCoW**: Must
**ペルソナ**: P-01 割当担当者（P-03 従事職員が受益者）
**要件**: FR-05.2, FR-05.3, SC-01

> **割当担当者** として、
> **ベースラインと最適化結果の差分を、総移動時間・総移動費用・最大移動時間・分布として提示したい**。
> なぜなら **上長・関係部署に削減効果を数値で示すことが、この PoC の目的そのものである** からだ。

### 受入基準

```gherkin
Scenario: 比較レポートを表示する
  Given ベースライン（実績）と最適化結果が揃っている
  When 担当者が比較レポートを開く
  Then 以下が表示される
    | 指標             | ベースライン | 最適化後 | 削減量 | 削減率 |
    | 総移動時間       | 450 時間     | 280 時間 | 170 時間 | 37.8% |
    | 総移動費用       | 850,000 円   | 520,000 円 | 330,000 円 | 38.8% |
    | 最大移動時間     | 95 分        | 48 分    | 47 分  | 49.5% |
  And 移動時間の分布（ヒストグラムまたは分位点）が表示される

Scenario: 比較レポートを CSV にエクスポートする
  Given 比較レポートが表示されている
  When 担当者が CSV エクスポートを実行する
  Then レポートの全指標を含む CSV が出力される

Scenario: 削減効果が負となる場合も正しく表示する
  Given 最適化結果の総移動時間が、ベースラインより長い
  When 比較レポートを表示する
  Then 削減量が負の値として表示され、増加していることが明示される
  # 重み設定によっては、時間が増えて費用が減ることがある
```

### 不変条件

- **新規**: 削減量 = ベースライン値 − 最適化後の値（符号を含めて常に成立する）
- **新規**: 重み w1（総移動時間）= 1.0、他が 0.0 のとき、最適化後の総移動時間 ≤ ベースラインの総移動時間

# 誤用・悪用シナリオ（SECURITY-11）

設計は正常系だけでなく、以下の誤用・悪用シナリオを考慮する。

## MU-01: 権限のない職員による他人の割当情報の閲覧（IDOR）

**シナリオ**: 攻撃者が、URL やリクエストパラメータの職員 ID を改変し、他の職員の居住小学校区や割当先を取得しようとする。

**対策**: すべてのリソース参照において、呼び出し元が当該リソースへのアクセス権限を持つことをサーバー側で検証する（SECURITY-08、オブジェクトレベル認可）。本 PoC では割当担当者のみが利用者だが、実運用で職員本人が利用者になる際にこの統制が不可欠となる（A-08）。

## MU-02: CSV インポートによる不正データの注入

**シナリオ**: 攻撃者が、数式インジェクション（`=cmd|...`）や過大なサイズのペイロードを含む CSV をインポートし、エクスポート先の Excel でコード実行を狙う、あるいはサービスを停止させる。

**対策**: 入力検証（SECURITY-05）— 型検査、長さ上限、書式の許可リスト検証。CSV エクスポート時に数式インジェクションを無害化する。リクエストボディのサイズ上限を設定する。

## MU-03: 総当たりによるログイン突破

**シナリオ**: 攻撃者が、庁内 IP を詐称した状態で、担当者アカウントに対しパスワードの総当たり攻撃を行う。

**対策**: 送信元 IP 許可リスト（US-02）に加え、アカウントロックまたは漸増遅延（SECURITY-12）。認証失敗の連続発生をアラート対象とする（SECURITY-14、US-04）。

## MU-04: 監査ログの隠蔽

**シナリオ**: 内部関係者が、不正な割当変更を行った後、監査ログを削除して痕跡を消そうとする。

**対策**: 監査ログを追記専用ストレージに保管し、アプリケーションロールに削除権限を与えない（SECURITY-14、US-04）。
