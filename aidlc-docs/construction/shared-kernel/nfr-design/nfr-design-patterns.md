## 2. パターン 1: ドメイン層の純粋性（Q1=A）

### 2.1 解決した緊張

| 決定 | 内容 |
|------|------|
| Application Design Q1=B | ヘキサゴナルアーキテクチャ。**ドメイン層は何にも依存しない**（フレームワークを含む） |
| NFR Requirements Q2=A | FastAPI + **Pydantic** による入力検証（SECURITY-05） |

`shared-kernel` のエンティティを Pydantic の `BaseModel` として実装すれば、バリデーションは宣言的に書け、DTO 変換も不要になる。しかし**ドメイン層が Web フレームワーク由来のライブラリに依存する**。ヘキサゴナルを採用した理由そのものが失われる。

### 2.2 採用するパターン

```text
+---------------------------------------------------------------+
|  U-07 api-orchestration                                       |
|                                                               |
|   Pydantic BaseModel（DTO）                                   |
|     - HTTP リクエスト / レスポンスの検証（SECURITY-05）       |
|     - OpenAPI スキーマの自動生成                              |
|                                                               |
|             |  変換                    ^  変換                |
|             v                          |                      |
+---------------------------------------------------------------+
                            |
                            v
+---------------------------------------------------------------+
|  U-01 shared-kernel                                           |
|                                                               |
|   frozen dataclass（ドメイン型）                              |
|     - __post_init__ による生成時バリデーション（BR-01〜BR-07） |
|     - 標準ライブラリのみに依存                                |
|                                                               |
+---------------------------------------------------------------+
```

**バリデーションは 2 か所に存在するが、目的が異なる。**

| 層 | 目的 | 失敗時の応答 |
|----|------|------------|
| **Pydantic（U-07）** | 外部からの入力が**構文的に**妥当か（型、必須項目、長さ上限、書式） | 400 Bad Request |
| **dataclass（U-01）** | 値が**業務上の不変条件**を満たすか（緯度の範囲、重みの非負性、資格別必要人数の合計） | ドメイン例外 → グローバルハンドラ → 汎用エラー |

**この二重化は冗長ではない。** U-01 のバリデーションは、CSV インポート（U-03）や最適化結果の構築（U-04）など、**HTTP を経由しない経路**でも働く。API 境界の検証だけでは、これらの経路が無防備になる。

### 2.3 却下した代替案

- **B（ドメインを Pydantic `BaseModel` にする）**: Pydantic の破壊的変更が 7 ユニットすべてに波及する。ヘキサゴナルの依存規則に反する
- **C（変換の自動生成）**: 自動生成の仕組みが追加の複雑さを持ち込む。本 PoC の型数（エンティティ 9 + 値オブジェクト 6）では、手書きの変換で十分に管理できる

### 2.4 コスト

`U-07 api-orchestration` が DTO ↔ ドメイン型の変換を書く必要がある。**これは意図的に支払うコストである。**

## 3. パターン 2: 全型の不変性（Q2=A）

### 3.1 解決した緊張

生成時バリデーション（BR-01〜BR-07）は、オブジェクトが可変であれば無意味である。

```text
c = Coordinates(latitude=35.0, longitude=139.0)   # BR-01 が検証する
c.latitude = 999.0                                # 可変なら、不変条件が壊れる
```

### 3.2 採用するパターン

**値オブジェクトとエンティティを、例外なくすべて frozen とする。**

- `@dataclass(frozen=True)` により、生成後の属性代入を禁止する
- 変更が必要な場合は、新しいインスタンスを生成する（`dataclasses.replace()`）
- `__post_init__` で生成時バリデーションを実行する

**この組み合わせにより、不変条件は「生成から破棄まで」維持される。** 生成を通過したオブジェクトは、その生涯にわたって不変条件を満たす。

### 3.3 エンティティも不変とすることの帰結

エンティティは同一性（ID）で識別されるため、属性の変更を許すのが一般的である。本設計はこれを許さない。

| 操作 | 従来の可変エンティティ | **本設計（frozen）** |
|------|---------------------|-------------------|
| 職員の居住小学校区を変更する | `staff.residenceDistrictId = "D003"` | `replace(staff, residence_district_id="D003")` |
| イベントのステータスを遷移させる | `event.status = Optimized` | `replace(event, status=OPTIMIZED)` |

**利点**:
- 変更のたびに `__post_init__` が再実行され、不変条件が再検証される
- 共有された参照が予期せず書き換わる事故が起こらない（`AssignmentProblem` は複数の `Staff` を保持する）
- ハッシュ可能になり、集合・辞書のキーとして使える

**U-03 への申し送り**: 永続化アダプタは frozen オブジェクトを扱う。ORM のダーティチェックに依存する更新パターンは使えない。明示的に新しいインスタンスを構築して保存する（申し送り U01-H21）。

### 3.4 `AssignmentResult` の不変性が持つ特別な意味

`AssignmentResult` の生成時バリデーション（BR-07）は、以下を拒否する。

- `violations` に `"C1"`, `"C2"`, `"C4"`, `"C5"` が含まれる（降格されるのは C3 のみ）
- `objectiveValue` が NaN・無限大・負値（INV-06）
- `assignments` に同一 `(eventId, staffId)` が 2 件以上（INV-01）

**frozen であるため、この検証を通過した結果は、以後決して壊れない。** ソルバーのバグが下流へ伝播する経路が、型のレベルで閉じられる。

## 4. パターン 3: 列挙値の境界変換（Q3=A）

### 4.1 3 か所に現れる同じ概念

| 場所 | 表記 |
|------|------|
| コード上の識別子 | `Position.MANAGER` |
| CSV の列値（担当者が Excel で作成する） | `管理職` |
| API の JSON 値 | `管理職` |

### 4.2 採用するパターン

**コード上は英語識別子とし、境界で日本語と相互変換する。変換表は 1 か所に集約する。**

```text
  CSV（日本語）        API JSON（日本語）
       |                      |
       |  U-03 CsvAdapter     |  U-07 DTO 変換
       v                      v
  +-------------------------------------+
  |  変換表（U-01 shared-kernel）       |
  |  Position.MANAGER  <-> "管理職"     |
  |  Position.GENERAL  <-> "一般職"     |
  |  ...                                |
  +-------------------------------------+
       |
       v
  コード（英語識別子）
```

**変換表を U-01 に置く根拠**: 変換は列挙型自身の性質であり、永続化にも API にも依存しない。U-03 と U-07 の双方が同一の変換表を使うことで、表記の不整合が起こらない。

### 4.3 却下した代替案

- **B（日本語識別子）**: Python の識別子として日本語を用いる。文法上は可能だが、リンタ・IDE・スタックトレースとの相性に懸念がある
- **C（CSV も英語識別子）**: **担当者が作る Excel に `MANAGER` と書かせる**ことになる。運用上の負担が大きく、入力誤りを誘発する

### 4.4 未知の値の扱い（fail closed）

CSV に変換表にない値（例: `課長補佐`）が現れた場合、**行番号とともにエラーを報告し、インポート全体をロールバックする**（SECURITY-15）。サイレントに `Other` へ丸めない。

## 5. パターン 4: `NewType` による識別子の区別（Q4=A）

```text
StaffId          = NewType("StaffId", str)
FacilityId       = NewType("FacilityId", str)
SchoolDistrictId = NewType("SchoolDistrictId", str)
DepartmentId     = NewType("DepartmentId", str)
EventId          = NewType("EventId", str)
```

**効果**: `mypy` strict モード（NFR Requirements Q11=A）が取り違えを検出する。`Assignment(staff_id=facility_id, ...)` は型エラーになる。

**実行時のオーバーヘッドはゼロ**である。`NewType` は静的型検査のみに作用し、実行時は素の `str` である。

**却下した代替案**:
- **B（専用クラス）**: 実行時にも型が区別されるが、CSV / JSON との相互変換にコードが必要になり、オーバーヘッドがある
- **C（素の `str`）**: 取り違えを検出できない。40 万の割当を扱うシステムで、施設 ID と職員 ID の取り違えは致命的である

## 6. パターン 5: 例外の構造（Q5=A）

### 6.1 階層

```text
DomainError（基底。構造化された文脈属性を持つ）
├── InvalidCoordinatesError
├── AllWeightsZeroError / NegativeWeightError
├── QualificationRequirementExceedsHeadcountError
├── DuplicateQualificationRequirementError
├── InvalidTravelParametersError
├── InconsistentDeclarationError
├── NonDemotableConstraintViolationError
├── InvalidStateTransitionError
└── AmbiguousDeclarationError
```

### 6.2 構造化された文脈属性

例外は、デバッグに必要な文脈を**属性として**持つ。メッセージ文字列には含めない。

| 属性 | 例 |
|------|----|
| `staff_id` | `S001` |
| `event_id` | `E001` |
| `facility_id` | `F010` |
| `violated_rule` | `BR-05` |

**個人情報（氏名、居住小学校区）を属性にもメッセージにも含めない**（SECURITY-03）。

### 6.3 3 層の応答（SECURITY-03, SECURITY-09, SECURITY-15）

| 層 | 内容 |
|----|------|
| **利用者への応答** | 汎用メッセージ。スタックトレース・内部パス・フレームワークバージョンを含めない |
| **構造化ログ** | 例外の型名と文脈属性（職員 ID、イベント ID、違反規則）。**氏名・居住小学校区を含めない** |
| **監査ログ**（U-06） | 職員 ID のみ |

**グローバルエラーハンドラは U-07 api-orchestration が設置する**（SECURITY-15: 「アプリケーションはグローバルなエラーハンドラを持たなければならない」）。

## 7. パターン 6: 個人情報のログ出力防止（Q6=A、多層防御）

### 7.1 2 層の防御（SECURITY-11: defense in depth）

| 層 | 手段 | 防ぐもの |
|----|------|---------|
| **構造的保証** | `src/security/` は `Staff` を import しない（リンタ規則。NFR-U01-R03 の検証方法として承認済み） | U-06 のコードから `Staff.name` を読む経路が**存在しない** |
| **実行時保証** | `Staff.__repr__` / `__str__` が氏名と居住小学校区を伏字にする（Q6=A） | 他ユニットが誤って `Staff` を `logger.info()` に渡しても、個人情報が出力されない |

**注**: Q6 は選択肢 A（伏字化）と B（リンタ規則）を代替案として提示したが、**B は既に承認済みの `nfr-requirements.md` で NFR-U01-R03 の検証方法として確定している**。Q6=A は「その上に伏字化を追加する」ことを意味する。結果として両者が並存し、多層防御が成立する。

### 7.2 伏字化の対象

```text
Staff(id=S001, department=D01, job_type=JobType.CLERICAL, position=Position.GENERAL,
      qualifications={...}, name=<redacted>, residence_district=<redacted>)
```

| 属性 | 伏字化 | 根拠 |
|------|:------:|------|
| `name` | **する** | 氏名は個人情報 |
| `residence_district_id` | **する** | 居住地は個人情報 |
| `id`, `department_id`, `job_type`, `position`, `qualifications` | しない | 個人を直接特定しない。デバッグに必要 |

### 7.3 `Staff` 以外の型

| 型 | 伏字化 | 根拠 |
|----|:------:|------|
| `Staff` | **する** | 氏名 + 居住小学校区 |
| `AvailabilityDeclaration` | **しない** | 職員 ID と理由区分のみ。氏名を持たない。ただし `reason_category` は健康・介護の事実を示すため、**監査ログには理由区分を記録しない**（U-06 へ申し送り） |
| その他 | しない | 個人情報を持たない |

**新たな申し送り（U01-H22）**: `AvailabilityDeclaration.reason_category` は「健康上の配慮」「育児・介護」という**要配慮個人情報に近い性質**を持つ。監査ログにはこれを記録せず、職員 ID と「申告が変更された」事実のみを記録する。**U-06 security の Functional Design で扱う。**

## 8. パターン 7: PBT のシード方針（Q8=A、PBT-08）

| 項目 | 決定 |
|------|------|
| CI でのシード | **実行ごとにランダム** |
| 失敗時 | **シードをログ出力する。シュリンクされた最小の反例も出力する** |
| 再現 | 記録されたシードで `--hypothesis-seed=<seed>` を指定して再現する |
| シュリンキング | **有効にする。無効化・迂回してはならない**（PBT-08） |
| 反例の恒久化 | PBT が発見した反例は、**例示ベーステストとして恒久的な回帰テストに追加する**（PBT-10） |

**固定シードを却下した根拠**: 固定シードは実行を完全に決定的にするが、**毎回同じ入力しか試さない**。PBT の目的は未知の入力空間を探索して未知のバグを見つけることであり、固定シードはこの能力を失わせる。失敗の再現性は、シードのログ出力によって確保される。

**Hypothesis の `.hypothesis/examples` ディレクトリ**（過去に失敗した入力を記憶する）は、ローカル開発では有効にする。CI では使わない（実行間で状態が持ち越されないため）。

## 9. パターン: fail closed の生成時バリデーション（NFR-U01-R01）

### 9.1 実装パターン

```text
@dataclass(frozen=True)
class Coordinates:
    latitude:  float
    longitude: float

    def __post_init__(self) -> None:
        if not (-90.0 <= self.latitude <= 90.0):
            raise InvalidCoordinatesError(...)
        if not (-180.0 <= self.longitude <= 180.0):
            raise InvalidCoordinatesError(...)
        if isnan(self.latitude) or isinf(self.latitude):
            raise InvalidCoordinatesError(...)
```

### 9.2 3 つの規律

1. **部分的に構築されたオブジェクトを返さない。** 検証に失敗したら例外を送出し、インスタンスは存在しない
2. **既定値で埋めない。** 不正な緯度を 0.0 に丸めるような処理をしてはならない
3. **frozen であるため、検証後に不変条件が壊れない**（パターン 2）

**この 3 つが揃って初めて、「型が存在する = 不変条件が成立している」と下流ユニットが仮定できる。**

## 10. パターン: 型の破壊的変更の管理（NFR-U01-R02）

U-01 の型は U-02〜U-07 の 6 ユニットから参照される。破壊的変更を CI で検出する。

| ゲート | 内容 |
|-------|------|
| **`mypy` strict** | 型の不整合を検出する。`NewType` による識別子の取り違えもここで捕捉する |
| **リンタ規則 R-2** | `src/shared-kernel/` は他のいかなるユニットも import してはならない（依存グラフの根） |
| **リンタ規則 R-3** | `src/distance-cost/` は `src/shared-kernel/` 以外を import してはならない（`C-01` の純粋関数性を機械的に保証する） |
| **リンタ規則（NFR-U01-R03）** | `src/security/` は `Staff` を import してはならない |
| **全ユニットのテスト実行** | U-01 の型を変更した際、6 ユニットのテストがすべて実行される |

## 12. 拡張ルール適合サマリ

### 12.1 Security Compliance

| ルール | 判定 | 根拠 |

| **SECURITY-03** アプリケーションログ | **適合** | 例外の文脈属性・メッセージ・`__repr__` のいずれにも氏名と居住小学校区を含めない（パターン 5, 6） |

| **SECURITY-09** ハードニング | **適合** | エラー応答にスタックトレース・内部パス・フレームワークバージョンを含めない（パターン 5.3） |

| SECURITY-01, 02, 04, 06, 07, 08, 10, 12, 13, 14 | **N/A** | U-01 は型定義のみ。暗号化・ネットワーク・HTTP ヘッダ・IAM・認証・認可・依存管理・監査ログのいずれの表出も持たない。U-03, U-06, U-07 および Infrastructure Design / Code Generation が対象 |

**ブロッキング所見: なし**
