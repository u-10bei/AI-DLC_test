### Question 1: C1 定員充足のセマンティクス（ハード制約）

FR-04.3 C1 は「必要人数が**ちょうど（または最低限）**割り当てられる」と両論併記です。確定してください。

A) **ちょうど（等号）**: 各施設 j に対し `Σ_i x_ij == required_headcount_j`。過剰派遣を防ぐ（職員負担・費用の観点で妥当）。総数が足りなければ実行不可能 → FR-04.5 の総数不足パスへ **（推奨）**

B) **最低限（≧）**: `Σ_i x_ij >= required_headcount_j`。余剰職員を配置しうる。総移動時間/費用の最小化がある限り最適解は等号に収束しがちだが、明示的に許す

C) 施設ごとに設定可能（既定は A）

### Question 2: 目的関数 3 項の正規化（多目的の重み付き和）

3 項はスケールが異なります（移動時間=秒、移動費用=円、公平性=最大移動時間の秒）。重み `w1,w2,w3` を意味あるものにするため、正規化しますか？

A) **各項を正規化してから重み付き和**をとる — 例: 総移動時間を「割当人数×代表移動時間」で、費用を「代表費用」でスケールし、無次元化する。正規化定数は設定として外部化（NFR-M03）。担当者の重み調整が直感的になる **（推奨）**

B) **生の値のまま重み付き和** — `w1·Σt + w2·Σc + w3·Tmax`。円と秒が混在し、重みの相対値の意味が担当者に伝わりにくい

X) Other

[Answer]:A

### Question 4: 実行不可能（infeasible）時の原因診断フロー（FR-04.5, 申し送り H-9）

「C3 のみが原因」をどう判定し、降格を適用しますか？

A) **段階的求解の決定木** — (1) 全ハード制約で solve。feasible なら通常解。(2) infeasible なら **C3 を除いた緩和問題**を solve。(2a) 緩和問題が feasible → 原因は C3 のみ → **C3 を big-M ソフトに降格して再 solve**（FR-04.5 の C3 パス）。(2b) 緩和問題も infeasible → (3) **総数チェック** `Σ available < Σ required` なら「総数不足」を報告（**C1 は降格しない**、追加申告を促す）。(4) それ以外は **C2/C4/C5 が原因**として該当制約を明示（降格しない）**（推奨。H-9 を解決する明快な決定木）**

B) 全ハード制約を一斉にソフト化して違反を観測 — 原因が混在し、どれが真の原因か切り分けにくい

### Question 5: C3 降格時の big-M の下限（申し送り H-10, INV-12）

C3 をソフト降格したとき、「C3 を 1 件でも満たせる解があれば必ずそれが選ばれる」ことを保証する big-M の決め方は？

A) **問題データから計算する厳密な下限** — big-M を「正規化後の目的関数が取りうる理論上限」より大きく設定する（例: `M = (達成可能な最大目的値) + 1`、正規化済みなら定数上界）。各 C3 違反に `M` のペナルティを課す。これにより **C3 違反を 1 件減らせるなら、他のどんな目的悪化よりも優先**される（INV-12）**（推奨。H-10 を解決）**

B) 十分大きい固定値（例: 1e9）を経験的に使う — 単純だが、正規化やデータ規模次第で INV-12 を破りうる（理論保証がない）

### Question 6: ソフト制約「従事履歴の平準化」（FR-04.4）の本 PoC でのスコープ

FR-04.4 は従事履歴の平準化をソフト制約とします。ただし履歴データは U-05 が扱い、**U-04 は U-05 に依存しません**（依存は U-01/02/03 のみ）。

A) **フックのみ実装（既定重み 0）** — 目的関数に履歴ペナルティ項の**構造だけ**用意し、既定重み 0 で無効化。過去従事回数の入力インターフェース（`AssignmentProblem` への追加フィールドまたはパラメータ）を定義し、履歴連携は将来（U-05/運用）に委ねる。**依存規則を壊さず、拡張点を残す** **（推奨、PoC スコープ）**

B) 本 PoC で履歴平準化を完全実装 — U-04 が過去従事回数を受け取り最適化に反映。ただし履歴の供給元（U-05）との連携設計が必要で、依存順（U-04 は U-05 の前）と矛盾しうる

X) Other

### Question 7: ピン留め再最適化（FR-06.4）と時間制限（FR-04.6）の扱い

再最適化と時間制限の設計方針を確定してください。

A) **ピン留めは固定変数、事前検証あり；時間制限は最良解+ギャップ** —
(1) ピン留め割当（`AssignmentProblem.pinned_assignments`）は対応する `x_ij` を 1 に固定して solve。
(2) **solve 前**にピン留めがハード制約（C1〜C5）に違反しないか検証し、違反すれば **solve せずエラー**（FR-06.4。担当者はピン留め解除後に再実行）。
(3) 時間制限（既定 300 秒, NFR-P02）内に厳密解が出なければ、**その時点の最良実行可能解と最適性ギャップ**を `AssignmentResult`（`TIME_LIMIT_REACHED` + `optimality_gap`）で返す（FR-04.6, US-20）**（推奨）**
