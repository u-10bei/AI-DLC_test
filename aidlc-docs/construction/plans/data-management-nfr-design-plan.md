## 1. 本ステージのスコープ

NFR Design は、確定済みの NFR 要件を **設計パターンと論理コンポーネント**に落とし込む。

**U-03 は実永続化を持つ最初のユニットである。** したがって、以下の設計判断が本ステージで生じる:

- トランザクション境界を誰が所有するか（fail closed の原子性、BR-DM01）
- DB からの復元時に不正データを検出したときの振る舞い（SECURITY-15）
- 距離キャッシュの全再計算を、小学校区マスタ更新に対してどう順序づけるか（一貫性）
- 永続化層での個人情報の扱い（SECURITY-03）

**既に確定済み（本ステージで再検討しない）**: SQLAlchemy Core + 手書きマッパ、`executemany` 一括挿入、相関サブクエリ、`connect` イベントでの PRAGMA、インメモリ SQLite テスト。

### Question 1: トランザクション境界の所有者（信頼性 / 性能、BR-DM01）

CSV インポートの原子性と、一般的な書き込み操作のために、トランザクション境界を誰が所有しますか？

A) **アプリケーションサービスのメソッドが所有する** — 各サービスメソッドがセッションを開き、commit / rollback する。CSV インポートサービスは「解析 + 検証 + 保存」を 1 トランザクションに包む。U-07 はサービスメソッドを呼ぶだけで、トランザクションを管理しない。単純・明示的で fail closed **（推奨）**

B) **明示的な Unit-of-Work オブジェクトを呼び出し側（U-07）が制御する** — commit 境界を U-07 が持つ。複数ステップ操作に柔軟だが、U-07 と永続化層の結合が強くなり、ヘキサゴナルのポート境界を越える

C) **文ごとの自動コミット** — BR-DM01 の原子性を壊すため却下

### Question 2: DB 復元時に不正データを検出したときの振る舞い（信頼性、SECURITY-15）

マッパが行を読み、ドメインの `__post_init__` がそれを拒否した（DB が破損している）場合、どう表面化させますか？

A) **`DomainError` のサブクラス（例: `DataIntegrityError`）を送出する** — 行の識別子（ID のみ、個人情報を含めない）を文脈に付す。fail closed で上位へ伝播し、不正・部分的なオブジェクトを決して返さない **（推奨、SECURITY-15）**

B) **ログに記録してその行をスキップし、正常な行だけ返す** — データを黙って落とすため却下（fail closed 違反）

C) **`None` / `Optional` を返す** — 検査をすべての呼び出し側に押し付けるため却下

### Question 3: CSV インポートのメモリ内処理モデル（性能、NFR-P04 / BR-DM02）

NFR-P04（2,000 行を 30 秒以内）と BR-DM02（全エラーを行番号付きで一括報告）のために、CSV をどう処理しますか？

A) **全行をロード → 全行を検証（エラーを行番号付きで蓄積）→ `executemany` で一括保存** — 1 パスをメモリ上で行う。2,000 行は小さく、全エラー一括報告と自然に両立する **（推奨）**

B) **ストリーミング / チャンク処理** — 2,000 行には過剰で、全エラー一括報告（BR-DM02）を複雑にする

### Question 4: 距離キャッシュ全再計算の順序性（一貫性 / 信頼性）

小学校区マスタの更新後に距離キャッシュを全再計算する（Functional Design で確定）際、マスタ更新トランザクションに対してどう順序づけますか？

A) **同一トランザクション** — 小学校区マスタの更新 + 距離キャッシュの再計算・保存を原子的に行う。いずれかが失敗すれば両方ロールバック（fail closed、古いキャッシュを残さない）**（推奨。一貫性が最も強い）**

B) **別トランザクション（コミット後）** — マスタは commit 済みだが、再計算が失敗するとキャッシュが古いまま残る。修復経路が必要になる

C) **遅延（Lazy）** — マスタ更新トランザクション内でキャッシュを削除（無効化）し、次回参照時に再計算する。コストを最初の最適化実行まで遅らせる

### Question 5: 永続化層での個人情報の扱い（セキュリティ、SECURITY-03）

職員マッパは DB から氏名・居住小学校区（個人情報）を読み込みます。永続化層でのログ/エラー方針を確定してください。

A) **永続化層は行の内容をログに出さない** — マッパのエラーには職員 ID と行番号のみを含める（BR-DM14）。SQLAlchemy の `echo` は全環境で `False`、SQL の値ログを無効にする **（推奨、SECURITY-03）**

B) **開発環境でのみ SQL echo を有効にする** — デバッグに便利だが、SQL の値（個人情報）がログに出る。SECURITY-03 違反のため却下
