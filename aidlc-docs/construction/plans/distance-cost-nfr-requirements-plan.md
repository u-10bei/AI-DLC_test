### 2.2 性能要件（NFR-P03）の分析

NFR-P03 は「距離行列（最大 1 万要素、Q4=A のキャッシュ圧縮後）を事前計算しキャッシュする」と定める。

**計算量の見積もり**:

| 小学校区数 D | キャッシュエントリ数 D(D+1)/2 | Haversine 計算回数 |
|:-----------:|:---------------------------:|:-----------------:|
| 100 | 5,050 | 5,050 |
| 200 | 20,100 | 20,100 |

Haversine 距離 1 回の計算は、三角関数を数回呼ぶだけである。**2 万回でも、素朴な Python ループで 1 秒未満で終わる見込みである。**

したがって NFR-P03 の「事前計算」は、性能上の必須要件というより、**キャッシュによる再計算の回避**が主眼である（US-14 でパラメータを変えるたびに再計算しない）。

## 3. 本ステージで決める論点

### 論点 1: NumPy を使うか（性能 vs 依存の最小性）

U-01 の NFR Requirements（tech-stack-decisions.md セクション 11）は、依存の一覧に `numpy` を「距離行列の事前計算」用途で挙げていた。

しかし U-02 の分析により、**距離行列の計算は素朴な Python ループでも 1 秒未満で終わる**ことが判明した。

一方、**U-02 のプロダクションコードは現在、標準ライブラリのみに依存している**（`math` のみ）。`numpy` を導入すると:

- U-02 のプロダクション依存が 1 件増える（SECURITY-10 の脆弱性スキャン対象が増える）
- リンタ規則 R-3（`distance_cost` は `shared_kernel` 以外を import してはならない）を、`numpy` を許可するよう緩める必要がある

→ **Question 1 で確認する。**

### 論点 2: オラクル実装（P-D05）をテスト依存として追加するか

P-D05（Haversine のオラクル検証、PBT-05）には、独立した測地線距離の実装が必要である。選択肢:

- `geopy`（測地線距離ライブラリ）を**テスト依存**として追加する
- 既知の座標ペアと実測距離の**表**をテストに埋め込む（追加依存なし）

→ **Question 2 で確認する。**

### Question 1: NumPy の要否（性能 / 依存の最小性）

距離行列の計算は、素朴な Python ループでも最大 2 万回で 1 秒未満です。NumPy を使いますか？

A) **使わない。標準ライブラリの `math` のみで実装する** — U-02 のプロダクション依存はゼロのまま。R-3 を緩めない。NFR-P03 の「事前計算」はキャッシュ（U-03 が永続化）で達成する。計算自体は十分高速 **（推奨）**

B) **使う** — 距離行列をベクトル化する。U-02 のプロダクション依存に `numpy` が加わり、R-3 を `numpy` を許可するよう緩める。計算は数十ミリ秒に短縮されるが、そもそも 1 秒未満であり体感差はない

### Question 2: オラクル実装の調達（P-D05、PBT-05）

Haversine 実装の正しさを、独立した測地線距離と比較して検証します（緯度経度の取り違えや `atan2` の引数誤りを検出するため）。

A) **既知の座標ペアと実測距離の表をテストに埋め込む** — 例: 東京駅〜大阪駅、東京駅〜横浜駅など、公表されている実距離。追加のテスト依存が不要。表は少数（5〜10 ペア）だが、実装誤りの検出には十分 **（推奨）**

### Question 3: 距離行列の事前計算をどのユニットが担うか（性能 / 責務）

NFR-P03 の「距離行列の事前計算」を、どのユニットが実行しますか？

A) **U-02 が事前計算の純粋関数を提供し、U-03 がそれを呼んで結果を永続化する** — U-02 は `compute_district_distance_matrix(districts) -> list[DistanceCacheEntry]` を提供する（純粋関数）。U-03 が結果を DB に保存する。小学校区マスタ更新時に U-03 が再計算を起動する **（推奨。純粋関数と永続化の責務が分離される）**

B) **U-03 が距離計算のループも所有する** — U-02 は 1 ペアの計算関数のみを提供し、ループは U-03 が書く。U-02 の責務が狭くなるが、計算ロジックが U-03 に漏れる

### Question 4: 浮動小数点の再現性（PBT-08 / 性能）

Haversine 計算は浮動小数点演算です。同じ入力に対し、実行環境（CPU、Python バージョン）が異なると、最下位ビットが変わりうる可能性があります。プロパティテストの再現性への影響を確定してください。

A) **INV-07b（キャッシュ経由の厳密等価）は同一プロセス内でのみ保証する** — キーの正規化により、同一プロセス内では `cached(a,b)` と `cached(b,a)` は必ず同一エントリを引くため厳密に等価。異なる環境間でのビット一致は要求しない（キャッシュは環境ごとに再計算される） **（推奨。現実的かつ十分）**

B) **異なる環境間でもビット一致を保証する** — 固定小数点演算などが必要になり、過剰
