# U-08 frontend — NFR Requirements 計画

**ユニット**: U-08 frontend（`src/frontend/`）
**ステージ**: NFR Requirements（このユニットの非機能要件の確定 + **フロントエンド技術スタックの決定**）。
**背景**: U01-H20 により、フロントエンドの技術スタック（言語・フレームワーク・**フロント側 PBT フレームワーク**）は U-08 で決定する。PBT 拡張（testing/property-based）は全ユニットでブロッキングのため、フロントにも PBT 戦略が必須。

---

## 1. 固定前提（質問しない — 記録のため明示）

- **通信境界**: REST/JSON over HTTP のみ（NFR-M05）。バックエンドのベース URL は外部化設定（NFR-M03、`config/`）。
- **ポーリング間隔**: 最適化ジョブは約 2 秒間隔（機能設計 Q4=A）。
- **描画対象**: 庁内イントラネット PC のデスクトップブラウザ。UI 言語は日本語。
- **SSR 不要**: 庁内向け業務ツールのため SPA または静的配信で足りる（SEO 不要）。
- **セキュリティ境界**: 認証・認可・IP 制限・レート制限・セキュリティヘッダはすべて **U-07（バックエンド）** が担う。フロントは Cookie（HttpOnly）を保持せず、`401` 捕捉で失効を扱う（機能設計 FE-50/52）。フロント固有のセキュリティ NFR は「XSS を招く実装をしない（危険な innerHTML 等を避ける）」に限られる。
- **バンドル配信**: フロントの静的アセットは U-07 と同一サーバーから配信してよい（PoC、A-07）。実運用でバックエンド分離時も REST 境界により無変更（NFR-M05）。

## 質問 1
フロントエンドの言語・フレームワーク・ビルドツールはどれにしますか？（バックエンドは Python + mypy strict の強い型付け規律を採用済み）

A) **React + TypeScript（+ Vite）** — 主流、静的型付けがバックエンドの型規律と整合、エコシステム最大。7 画面規模の PoC でも将来拡張に耐える。

B) **Vue 3 + TypeScript（+ Vite）** — 学習コスト低め、単一ファイルコンポーネント。

C) **Svelte / SvelteKit + TypeScript** — 記述量少・軽量バンドル。

D) **最小構成: TypeScript + 軽量ビューライブラリ（重量級フレームワークなし）** — 7 画面の PoC に対する最小フットプリント。

E) その他（[Answer]: タグの後に記述してください）

[Answer]:A

## 質問 2

## 質問 4

B) **ベストエフォートのみ**（セマンティック HTML は用いるが、PoC では正式な準拠目標を置かない）。
