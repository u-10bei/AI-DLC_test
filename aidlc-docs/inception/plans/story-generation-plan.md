## 1. 目的とスコープ

本計画は、承認済みの要件（FR-01〜FR-07、NFR-P/S/T/M 各群）を、INVEST 基準を満たすユーザーストーリーと受入基準に変換するための方法論と手順を定義する。

**本計画で扱わないこと**: 優先順位付け、スプリント計画、開発タスクへの分解、技術的な実装方式の決定。これらは後続ステージ（Workflow Planning 以降）で扱う。

## 3. ストーリー分解アプローチの選択肢

以下のアプローチから選択する。トレードオフを併記する。

### A) User Journey-Based（ユーザージャーニー基準）
ストーリーを担当者の作業フロー順に並べる（イベント登録 → データ投入 → パラメータ設定 → 最適化実行 → 結果確認 → 手動調整 → レポート出力）。

- **利点**: 業務の流れに沿うため、担当者がレビューしやすい。欠落した手順に気づきやすい
- **欠点**: 横断的関心事（認証、監査ログ）が特定のジャーニーに埋もれやすい

### B) Feature-Based（機能基準）
ストーリーをシステム機能単位で組織する（イベント管理、マスタ管理、最適化エンジン、レポート、認証）。

- **利点**: 要件（FR-01〜FR-07）と 1 対 1 に近く対応し、トレーサビリティが明瞭
- **欠点**: 個々の機能がユーザーにもたらす価値が見えにくくなりやすい

### C) Persona-Based（ペルソナ基準）
ストーリーをユーザータイプ別に分類する（割当担当者、システム管理者、割当される職員）。

- **利点**: 誰のための機能かが明確。本 PoC では「割当される職員」が目的関数の対象であるため、価値の追跡に適する
- **欠点**: 本 PoC の直接利用者は割当担当者にほぼ限定されるため、分類が偏る

### D) Domain-Based（ドメイン基準）
業務ドメイン単位で組織する（イベント管理ドメイン、職員ドメイン、最適化ドメイン、レポーティングドメイン）。

- **利点**: 後続の Application Design / Units Generation でのコンポーネント分割にそのまま接続しやすい
- **欠点**: ユーザー価値よりシステム構造に寄る

### E) Epic-Based（エピック階層）
エピック（大きな価値の塊）の下にサブストーリーを配置する階層構造。

- **利点**: 規模の大きい要件（最適化エンジン）を段階的に詳細化できる
- **欠点**: 階層が深くなると管理コストが増す

### F) Hybrid（推奨候補）
**エピック（Epic-Based）を骨格とし、各エピック内はユーザージャーニー順（A）に並べ、横断的関心事（認証、監査ログ）は独立したエピックとして切り出す。**

- **利点**: 業務の流れとトレーサビリティを両立し、横断的関心事の埋没を防ぐ
- **欠点**: 分類ルールを事前に定める必要がある
