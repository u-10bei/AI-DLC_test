# 共有インフラ設計（Shared Infrastructure）— バックエンド全体

**作成日**: 2026-07-09
**ステージ**: CONSTRUCTION - Infrastructure Design（U-01 のスロットで作成。バックエンド全体を対象とする）
**拘束範囲**: **U-01 〜 U-07**（U-08 frontend は別途）

---

## 0. 本文書の位置づけ

本システムは**モノリス**（Units Generation Q1=A）であり、**単一サーバー**（A-07）で稼働する。U-01 〜 U-07 は同一のプロセス・同一の DB・同一のファイルシステムを共有する。**すべてのインフラが共有インフラである。**

**U-02 〜 U-07 の Infrastructure Design ステージは、本文書を参照する。** 各ユニットがインフラを再導出してはならない。

**U-01 自身はインフラ表出を持たない。** その記録は `construction/shared-kernel/infrastructure-design/` に置く。

## 1. デプロイ環境（Deployment Environment）

### 1.1 PoC の構成（A-07）

フロントエンドとバックエンドを**同一のインターネット側サーバー**上で稼働させる。庁内イントラネット PC からアクセスする。

```text
  +---------------------+                +----------------------------------+
  |  Intranet PC        |                |  Existing Exposure Platform      |
  |  (municipal LAN)    |                |  (pre-existing, A-06)            |
  |                     |                |  - TLS termination               |
  |                     |     HTTPS      |  - Access logging  (SECURITY-02) |
  |                     |--------------->|  - WAF                           |
  +---------------------+                +----------------------------------+
                                                        |
   allowlist: municipal egress global IP                |
   (NFR-S10.2, enforced by SEC-03)                      v
                                         +----------------------------------+
                                         |  PoC Server (internet-side)      |
                                         |                                  |
                                         |  +----------------------------+  |
                                         |  |  Frontend (U-08)           |  |
                                         |  +----------------------------+  |
                                         |  |  Backend process (U-01..07)|  |
                                         |  |    FastAPI + uvicorn       |  |
                                         |  +----------------------------+  |
                                         |  |  Job worker process (U-04) |  |
                                         |  +----------------------------+  |
                                         |                                  |
                                         |  +----------------------------+  |
                                         |  |  Encrypted volume          |  |
                                         |  |    app.db (SQLite)         |  |
                                         |  |    audit/*.jsonl (append)  |  |
                                         |  +----------------------------+  |
                                         +----------------------------------+
```

### 1.2 既存の公開基盤が提供する統制（Q3=A、申し送り H-6 の解消）

要件 A-06 の既存基盤は、以下を**すべて提供する**。

| 統制 | 提供 | 対応する SECURITY ルール |
|------|:----:|----------------------|
| TLS 終端 | **あり** | SECURITY-01（転送時の暗号化） |
| アクセスログ | **あり** | **SECURITY-02**（ネットワーク中継機器のアクセスログ） |
| WAF | **あり** | SECURITY-11 の追加強化策 |

**これにより SECURITY-02 は適合する。** 申し送り H-6 は解消された。

**注**: WAF は要件 v1.3 の NFR-S10 で「任意の追加強化策」として記載していたが、既存基盤が既に提供しているため、追加コストなく利用できる。

### 1.3 実運用時の構成（PoC 対象外）

バックエンドを庁内オンプレミスへ分離する。**Q9=B（Units Generation）により、実運用のデプロイ構成は PoC のユニット境界とは無関係に再構成する。** ただし NFR-M05（明示的な API 境界とエンドポイント URL の外部化）は引き続き必須である。

## 2. コンピュート（Compute Infrastructure）

| プロセス | 内容 | 所有ユニット |
|---------|------|------------|
| **API プロセス** | FastAPI + uvicorn。HTTP リクエストを処理する | U-07（U-01〜U-06 を含む） |
| **ジョブワーカープロセス** | 最適化ジョブを実行する。DB のジョブテーブルをポーリングする | **U-07**（U-04 の求解ロジックを実行）<br>*訂正 2026-07-17（U07-H14）: 当初 U-04 と記載していたが、U-04 NFR Requirements Q5=A で「U-04 は求解ロジックと SolverPort を提供し、ジョブ実行の配線は U-07 が行う」と確定し、U-07 Functional Design Q4=A でキューとワーカーのコードを U-07 に置いた。プロセスの存在と分離の根拠は不変で、所有ユニットの記載のみを訂正する。* |

**プロセス分離の根拠**: 最適化計算は最大 300 秒を要する（NFR-P02）。API プロセス内で実行すると、その間 HTTP リクエストの処理が阻害される。**別プロセスとすることで、API の応答性を保つ。**

**ワーカーは単一プロセスとする。** SQLite は単一ライタであり、複数ワーカーは書き込み競合を増やすだけである。同一イベントにつき同時 1 ジョブという制約（Application Design Q3=A）とも整合する。

**スケーリング**: 行わない。PoC は単一サーバー構成であり、稼働率目標（SLA）を定めない（NFR Requirements Q10=A）。レジリエンシー拡張は無効である。

## 3. ストレージ（Storage Infrastructure）

### 3.1 保存されるデータ

| データ | 形式 | 所有ユニット | 個人情報 |
|-------|------|------------|:--------:|
| 業務データ（職員、施設、イベント、従事可否申告、割当結果） | SQLite ファイル `app.db` | U-03 | **含む**（氏名、居住小学校区） |
| 距離キャッシュ（小学校区ペア） | 同上（テーブル） | U-02 定義 / U-03 実装 | 含まない |
| ジョブ状態 | 同上（テーブル） | U-04 | 含まない |
| セッション | 同上（テーブル） | U-06 | 含まない |
| **監査ログ** | **追記専用ファイル `audit/*.jsonl`** | U-06 | **含まない**（職員 ID のみ） |

### 3.2 保存時の暗号化（Q4=A、SECURITY-01、申し送り U01-H17 の解消）

**要件**: アプリケーションのデータディレクトリ（`app.db` と `audit/` の双方）は、**暗号化されたボリューム上に配置しなければならない**。

| 環境 | 手段の例 |
|------|---------|
| Linux オンプレミス | LUKS による暗号化ボリューム |
| クラウド | 暗号化ディスク（プロバイダのマネージド鍵、または顧客管理鍵） |

**具体的な手段は運用環境に委ねる。** 本設計が定めるのは「データディレクトリが暗号化ボリューム上にあること」という**要件**である。

**この方針が有効な根拠**: SQLite の標準ビルドには暗号化機能がない（NFR Requirements で確認済み）。ファイルシステム / ディスクレベルの暗号化は DB 製品に依存せず、**実運用の PostgreSQL でもそのまま通用する**。

**PoC でも暗号化を省略しない根拠**: 過去実績データは仮名化される（氏名を職員 ID に置換、CQ7=B）。しかし**居住小学校区は仮名化されずに残る**。小学校区と所属部署と役職の組み合わせは、個人を特定しうる。暗号化の省略は SECURITY-01 のブロッキング所見となる。

### 3.3 監査ログの追記専用ファイル（SECURITY-14）

#### 配置と属性

| 項目 | 内容 |
|------|------|
| 形式 | JSON Lines（1 行 1 エントリ） |
| 配置 | 暗号化ボリューム上の `audit/` ディレクトリ |
| 属性 | **`chattr +a`（追記専用）** |
| 属性の付与 | **root（`CAP_LINUX_IMMUTABLE` を持つ）が行う。アプリケーションは行えない** |
| ファイルシステム | ext4 または XFS（`chattr +a` に対応すること） |

#### アプリケーションプロセスにできること・できないこと

| 操作 | 可否 |
|------|:----:|
| ファイル末尾への追記 | **可能** |
| 既存行の書き換え | 不可 |
| 切り詰め（truncate） | 不可 |
| 削除・改名 | 不可 |

**`P-04 AuditLogPort` が削除・更新のメソッドを定義しない**（型レベル）ことと、OS の強制（実行時）が**二重に働く**（SECURITY-11、defense in depth）。

#### 保持期間の管理（Q5=A、SECURITY-14、申し送り U01-H16 の解消）

SECURITY-14 は監査ログの **90 日以上の保持**を要求する。一方、追記専用ファイルはアプリケーションからローテーションできない。

**特権プロセス（cron 等）が、日次で以下を実行する。**

```text
  毎日 00:00（特権プロセス、アプリケーションとは別のアカウント）
       |
       +--> 1. 現在のファイルから追記専用属性を外す
       |        chattr -a audit/current.jsonl
       |
       +--> 2. 日付付きの名前へローテーションする
       |        mv audit/current.jsonl audit/2026-07-09.jsonl
       |
       +--> 3. ローテーション後のファイルに追記専用属性を再付与する
       |        chattr +a audit/2026-07-09.jsonl
       |
       +--> 4. 新しい current.jsonl を作成し、追記専用属性を付与する
       |        touch audit/current.jsonl && chattr +a audit/current.jsonl
       |
       +--> 5. 90 日を超えた古いファイルのみを削除する
                find audit/ -name '*.jsonl' -mtime +90 -delete
```

**重要**: この特権プロセスは、**アプリケーションとは別のアカウント**で動作する。アプリケーションのアカウントは `chattr` を実行できず、`audit/` ディレクトリへの書き込み権限も持たない（`current.jsonl` への追記権限のみを持つ）。

**SECURITY-14 の要求「アプリケーションのロールが自身のログを削除する権限を持たない」を満たす。**

### 3.4 バックアップ

DB ファイルの定期ダンプのみを行う。**RPO / RTO は定めない**（NFR Requirements Q10=A、レジリエンシー拡張は無効）。

## 4. メッセージング（Messaging Infrastructure）

**外部のメッセージングミドルウェアを導入しない。** Redis も RabbitMQ も使わない（NFR Requirements Q5=A）。

| 項目 | 内容 |
|------|------|
| ジョブキュー | **DB のテーブル**（SQLite / PostgreSQL） |
| ワーカー | ジョブテーブルをポーリングする単一プロセス |
| 所有ユニット | U-04（`P-05 JobStorePort`, `A-06 JobRunnerAdapter`） |

### 4.1 SQLite の必須設定（申し送り U01-H15）

**推奨ではなく必須である。**

| 設定 | 値 | 理由 |
|------|----|------|
| `PRAGMA journal_mode` | **`WAL`** | 読み取りと書き込みを並行させる。API プロセスとワーカープロセスが同一ファイルに触れるため |
| `PRAGMA busy_timeout` | **5000 ms 以上** | 書き込み競合時に即座に `database is locked` で失敗せず待機する |
| `PRAGMA foreign_keys` | **`ON`** | SQLite は既定で外部キー制約を強制しない |

### 4.2 トランザクション外での計算（申し送り U01-H19）

**最適化の計算は、書き込みトランザクションの外で実行しなければならない。** SQLite は単一ライタであり、300 秒の書き込みトランザクションは API プロセスを停止させる。

ジョブの起動（`enqueue`）と結果の保存は、それぞれ短いトランザクションで完結させる。計算そのものはトランザクション外で行う。

## 5. ネットワーク（Networking Infrastructure）

### 5.1 アクセス経路と統制

```text
  Intranet PC
       |
       |  (1) HTTPS
       v
  Existing Exposure Platform  ... TLS termination, access log, WAF（Q3=A）
       |
       |  (2)
       v
  SEC-03 NetworkControlModule ... 送信元 IP 許可リスト（NFR-S10.2）
       |                           庁内イントラネットの出口グローバル IP のみ
       |                           許可リストは ConfigPort から取得（NFR-M03）
       v
  SEC-04 RateLimitModule      ... レート制限（SECURITY-11）
       |
       v
  SEC-01 AuthenticationModule ... ログイン制限（NFR-S10.1）
       |                           セッション検証、アカウントロック
       v
  SEC-02 AuthorizationModule  ... deny by default、オブジェクトレベル認可
       |
       v
  SEC-05 InputValidationModule ... 型・長さ・書式・サイズ上限
       |
       v
  Application Services (U-01..U-07)
```

### 5.2 SECURITY-07 の文書化された例外

SECURITY-07 は「公開ロードバランサの 80/443 以外に `0.0.0.0/0` からの受信を許可してはならない」と定める。本 PoC のサーバーはインターネット側に配置されるが、SECURITY-07 はルール自体が文書化された例外を許容する。

**代償統制**:

| ID | 統制 | 所有 |
|----|------|------|
| **NFR-S10.1** | ログイン制限（未認証リクエストは業務ロジックに到達しない） | U-06 `SEC-01` |
| **NFR-S10.2** | 庁内イントラネットの出口グローバル IP のみを許可 | U-06 `SEC-03` |

**この 2 統制により、実質的な到達可能範囲は庁内イントラネットの認証済み利用者に限定される。**

許可リストは設定として外部化する。ハードコードしない（NFR-M03）。

## 7. 最小権限（SECURITY-06）

**IAM ポリシーは存在しない**（クラウドのマネージドサービスを使わないため）。代わりに、**OS レベルのファイルシステム権限**が最小権限の統制となる。

| 主体 | 権限 |
|------|------|
| **アプリケーションアカウント**（API プロセス、ワーカープロセス） | `app.db` への読み書き。`audit/current.jsonl` への**追記のみ**。`audit/` ディレクトリへの書き込み権限を持たない。`chattr` を実行できない |
| **監査ログ管理の特権プロセス**（cron） | `audit/` の全操作。`chattr` の実行。**業務 DB への権限を持たない** |
| **その他のアカウント** | データディレクトリへの権限を持たない |

**責務の分離**: アプリケーションは監査ログを追記できるが削除できない。特権プロセスは監査ログを管理できるが業務データに触れない。

## 9. 実運用移行時の差分

| 項目 | PoC | 実運用 | 影響を受けるインフラ |
|------|-----|--------|-------------------|
| DB | SQLite | **PostgreSQL** | 接続文字列の変更 + マイグレーション再適用（SQLAlchemy + Alembic、U01-H18） |
| バックエンドの配置 | インターネット側サーバー（フロントと同居） | **庁内オンプレミス** | Q9=B により、ユニット境界とは無関係に再構成する |
| 監査ログの改竄防止 | OS レベルの追記専用ファイル | **同じ仕組みが使える**。または PostgreSQL のロールと権限 | **再設計不要** |
| 保存時暗号化 | 暗号化ボリューム | **同じ仕組みが使える** | **再設計不要** |
| 従事可否の入力主体 | 担当者が代理で CSV 一括登録 | 職員本人がログインして申告 | U-06 に 500〜2,000 人分のアカウント管理が必要（A-08） |

**監査ログの統制と暗号化が、PoC と実運用で同一の仕組みで実現できる点が重要である。** 移行時に統制を再設計する必要がない。
