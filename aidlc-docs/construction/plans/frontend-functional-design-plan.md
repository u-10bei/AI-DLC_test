# U-08 frontend — 機能設計（Functional Design）計画

**ユニット**: U-08 frontend（`src/frontend/`）
**依存**: U-07 api-orchestration — **REST/JSON over HTTP のみ**（NFR-M05）。バックエンドユニットのプロセス内 import は禁止（H-5、Code Generation でリンタ／ビルド規則により機械的に検証）。
**Per-unit ループ**: 8 ユニット中 8 番目（最終ユニット）。
**ステージ**: 機能設計（技術非依存 — フロントエンドフレームワークは NFR Requirements で決定し、ここでは決めない）。

## 0. 前提コンテキスト: 消費可能な API 表面（回答前に必読）

U-08 は U-07 が実際に公開しているものしか描画できません。現在の U-07 REST 表面は以下のとおりです。

| ストーリー領域 | U-07 が公開しているエンドポイント |
|-----------|------------------------------|
| セッション（US-01） | `POST /sessions`（ログイン）、`DELETE /sessions`（ログアウト） |
| ヘルス | `GET /health` |
| イベント（US-05） | `POST /events`、`GET /events/{id}` |
| 職員マスタ（US-07） | `POST /masters/staff/import`、`GET /masters/staff/export` |
| 従事可否申告（US-11） | `POST /events/{id}/declarations/import` |
| 充足状況（US-13） | `GET /events/{id}/sufficiency` |
| 最適化（US-16/17/20/24） | `POST /optimizations`、`GET /optimizations/{job_id}` |
| 割当（US-21/22） | `GET /events/{id}/assignments`、`PATCH /events/{id}/assignments` |

**バックエンドのエンドポイントが存在しないストーリー**（フロントから呼べない）:

- **US-06** イベントの編集／削除、およびイベント**一覧**（作成 + 単一取得のみ存在）
- **US-08** 施設インポート、**US-09** 小学校区インポート（*職員*インポートのみ存在）
- **US-12** 追加申告の履歴
- **US-25** 割当結果の CSV エクスポート（*職員*エクスポートのみ存在）
- **US-26 / US-27 / US-28** 比較レポートとベースライン入力 — `GET /events/{id}/comparison` は**意図的に未接続**で、U05-H6（繰り越された `historical_assignments` / `historical_declarations` テーブル）に閊えている。これは PoC の目玉である SC-01「移動時間 91.96% 削減」の見せ場。

公開済みエンドポイントだけでも、一つの完結した誠実なフローになる:
**ログイン → イベント作成 → 職員インポート → 申告インポート → 充足確認 → 最適化実行（ポーリング）→ 割当の閲覧／手動修正。**

セクション 3 の質問で、残りをどこまで U-08 が扱うか、比較画面をどうするかを決める。

## 1. 固定前提（質問しない — 記録のため明示）

- **UI 言語**: 日本語（庁内利用者 P-01 割当担当者 / P-02 システム管理者）。
- **対象**: 庁内イントラネット PC のデスクトップブラウザ（US-02 により送信元 IP は庁内出口に制限）。
- **通信**: REST/JSON のみ。バックエンドのベース URL は外部化設定（NFR-M05、NFR-M03 `config/`）。
- **セッション**: Cookie は HttpOnly（JS から読めない、BR-API21）— フロントはトークンを保持せず、Cookie が自動送信されることに依拠し、`401` を捕捉して失効を検知する。
- **ログインするペルソナ**: P-01 と P-02 のみ。P-03（従事職員）は PoC の UI を操作しない（A-08 — 申告は代理で一括登録）。

## 質問 1
PoC フロントエンドが扱う画面スコープはどれにしますか？

A) **公開済みエンドポイントの全フロー** — 実在する U-07 エンドポイントを持つ画面をすべて作る（ログイン、イベント作成／閲覧、職員インポート／エクスポート、申告インポート、充足状況、最適化実行 + ポーリング、割当一覧 + 手動修正）。エンドポイントの無いストーリーは繰り越し、申し送りに列挙する。（バックエンド変更ゼロで今日作れる。）

B) **最小の価値実証フローのみ** — ログイン → 最適化実行 → 割当一覧。マスタ／イベント／申告は事前投入済みと仮定し、インポート／充足の画面は省く。

C) **全 28 ストーリーの画面** — 全ストーリーをカバーするよう U-08 を拡張する。そのためにまず不足しているバックエンドエンドポイント（施設／小学校区インポート、イベント編集／削除／一覧、割当 CSV エクスポート、比較）を U-07/U-03/U-05 に追加する必要がある。スコープが大幅に拡大し、完了済みユニットを再度開く。

## 質問 2
比較／削減効果レポート（US-27）は PoC の目玉（SC-01: 移動時間 91.96% 削減）ですが、`GET /events/{id}/comparison` は未接続で、U05-H6 の繰り越し済み履歴テーブルに閊えています。U-08 の比較画面をどう扱いますか？

A) **完全に繰り越す** — 今回の PoC では比較画面を作らず、U05-H6 が入った後に作る申し送りとして記録する。価値ストーリーは代わりに、割当画面で取得可能な before/after の移動指標として示す。

B) **U05-H6 を今解消する** — `historical_assignments` / `historical_declarations` テーブルを追加し `GET /events/{id}/comparison` を公開してから、実データの比較画面を作る。目玉を PoC 必須と位置づけ、U-08 の前後で U-03/U-05/U-07 にバックエンド作業を追加する。

C) **明示的なプレースホルダで描画する** — 取得可能なデータから計算した／スタブの比較を描画する比較画面を作り、非本番であることを明示する。繰り越しテーブルに触れずにデモ用のビジュアルを用意する。

## 質問 4
`GET /optimizations/{job_id}` をポーリングする間、最適化ジョブの進捗をどう表示しますか？（求解は別のワーカープロセスで走る）

A) **固定間隔ポーリング**（約 2 秒）で終端状態まで状態表示。SUCCEEDED で最適性ギャップ + 経過時間、INFEASIBLE で不足診断（BR-API15）、FAILED で汎用エラーを表示。

B) **バックオフ付きポーリング**、スピナーのみ最小表示、終端状態で結果かエラーを表示。
