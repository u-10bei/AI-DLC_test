## 3. 所見 1: 文書の不整合（修正提案）

**`shared-infrastructure.md` セクション 2 は、ジョブワーカープロセスの所有ユニットを「U-04」と記載している。**

しかし、その後に確定した設計では:

- **U-04 NFR Requirements Q5=A**: 「U-04 は**求解ロジックと SolverPort を提供**する。**ジョブ実行の配線は U-07 が行う**」
- **U-07 Functional Design Q4=A / NFR Design LC-06/LC-08**: **キューとワーカーのコードは U-07** にあり、その中で U-04 の求解ロジックを呼ぶ

**プロセスの存在もその根拠（300 秒の分離）も変わらない。** 変わったのは「どのユニットがワーカーのコードを所有するか」というラベルだけである。

**提案**: `shared-infrastructure.md` セクション 2 の所有ユニットを **U-04 → U-07（U-04 の求解ロジックを実行）** に **in-place 修正**する。これは **U-02 が U-01 の承認済み `tech-stack-decisions.md` から numpy の記載を取り消した**のと同じ扱いである（後続ステージの分析により、先行文書の記述が正確でなくなった場合の訂正）。

**影響**: なし（記述の正確性のみ）。ブロッキングではない。

## 4. 所見 2: Code Generation を拘束する制約（申し送り化）

**`shared-infrastructure.md` セクション 5 は次を定めている**:

> **「最適化の計算は、書き込みトランザクションの外で実行しなければならない。」** SQLite は単一ライタであり、**300 秒の書き込みトランザクションは API プロセスを停止させる**。ジョブの起動（`enqueue`）と結果の保存は、それぞれ短いトランザクションで完結させる。**計算そのものはトランザクション外で行う。**

**本設計は既にこれに適合している**:

```text
claim:  UPDATE ... WHERE state='QUEUED'     ← 短いトランザクション（DP-03）
solve:  OptimizationService.optimize(...)    ← トランザクションの外（最大 300 秒）
save:   save_assignment_result(...)          ← 短いトランザクション
```

ただし、**実装時に「ワーカーが便利だからと `engine.begin()` の中で solve を呼ぶ」ことは容易に起こりうる**。その瞬間、**API プロセスが最大 300 秒停止する**。

**申し送り（U07-H13）として明記**し、Code Generation で遵守する。

## 5. `argon2-cffi` / `fastapi` / `uvicorn` はインフラ設計対象ではない

いずれも**アプリケーション依存**であり、インフラサービスではない。Code Generation で固定・pip-audit/SBOM を行う（U07-H9）。uvicorn の常駐（systemd/supervisor）は**運用の設定**であり、U-01 が既に「API プロセス + ワーカープロセス」として規定済み。
