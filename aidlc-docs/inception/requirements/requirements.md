## 1. Intent Analysis（意図分析）

### 1.1 ユーザーリクエスト（原文）

> 災害発生時の避難所応援や選挙事務に従事する職員を決定する際に、現在は職場単位で割り当てが行われているため、従事者の居住地から遠い場所に派遣されることがあり、①移動時間が長くかかることによる職員の負担感の増加、②タクシーなど移動にかかる費用の高額化といった問題が発生します。

### 1.2 分析結果

| 項目 | 判定 |
|------|------|
| Request Clarity | Clear（明確化質問により確定） |
| Request Type | New Project（グリーンフィールド） |
| Scope Estimate | Multiple Components（最適化エンジン、データ管理、Web UI、レポート） |
| Complexity Estimate | Complex（組合せ最適化 + 個人情報 + 複数制約 + 多目的関数） |
| Requirements Depth | Comprehensive |

### 1.3 問題の本質

現行の割当方式は**職場単位**である。すなわち、割当の決定変数が「職員の勤務地」に紐づいており、「職員の居住地」が一切考慮されていない。その結果、居住地から遠い施設に派遣される職員が発生し、以下の損失が生じている。

- **職員の負担**: 移動時間の増大。特に災害発生時は交通機関が不安定であり、参集の遅延にも直結する
- **財政的損失**: 長距離移動に伴う交通費の増大。特にタクシー利用時の費用が高額化する

本システムは、割当の決定基準に**居住地からの距離**を導入することでこの損失を削減する。数理最適化の観点では、これは職員を施設に割り当てる**一般化割当問題（Generalized Assignment Problem, GAP）**に帰着する。

## 2. スコープ

### 2.1 対象範囲（In Scope）

- 災害発生時の**避難所応援職員**の割当（今回の実装・検証対象）
- 「イベント」を第一級エンティティとするデータモデル設計（担当者が任意のイベントを登録可能な汎用構造）
- 職員・施設・小学校区マスタの管理（CSV/Excel 一括インポート + 個別手動修正）
- 距離・移動時間・移動費用の算出
- 多目的重み付き最適化による割当計算
- 割当結果の一覧出力（画面表示・CSV エクスポート）
- 現行方式（職場単位割当）との比較レポート（総移動時間・総移動費用の削減効果）
- 担当者による割当結果の手動修正と再計算

## 3. 機能要件（Functional Requirements）

### FR-01: イベント管理

- **FR-01.1**: 担当者は「イベント」を登録・編集・削除できる。イベントは種別（災害時避難所応援 / 選挙事務 / その他）、名称、実施日、ステータスを持つ
- **FR-01.2**: イベントは第一級エンティティとして設計され、種別に依存しない共通の割当エンジンから参照される
- **FR-01.3**: 今回の実装では、種別「災害時避難所応援」のみを検証対象とする。他種別のイベント登録は可能だが、動作検証は行わない

### FR-02: マスタデータ管理

- **FR-02.1**: 職員データを CSV / Excel から一括インポートできる。職員は以下の属性を持つ
  - 職員 ID、氏名、所属部署、職種、役職、保有資格、居住小学校区

  **注**: 従事可否は職員の属性ではない。イベントごとに変動するため、独立したエンティティとして FR-02.7 で定義する
- **FR-02.2**: 施設（避難所）データを CSV / Excel から一括インポートできる。施設は以下の属性を持つ
  - 施設 ID、施設名、所在小学校区、必要人数、必要職種・資格の内訳
- **FR-02.3**: 小学校区マスタを CSV / Excel から一括インポートできる。小学校区は以下の属性を持つ
  - 小学校区 ID、小学校区名、代表点の緯度、代表点の経度（= 当該小学校の所在地座標）
- **FR-02.4**: インポート済みデータを画面上で個別に追加・修正・削除できる（一括入力の補正手段）
- **FR-02.5**: インポート時にバリデーションを行い、不正データ（必須項目欠落、存在しない小学校区 ID の参照、緯度経度の範囲外など）を行単位でエラー報告する。1 行でもエラーがある場合、既定ではインポート全体をロールバックする（fail closed / SECURITY-15）
- **FR-02.6**: 職員の過去の従事履歴（イベント ID、従事日、施設 ID）を保持する
- **FR-02.7**: **従事可否申告**を独立したエンティティとして保持する。従事可否は職員とイベントの組に対して定まる（同一職員がイベント A には従事可能、イベント B には従事不可となりうる）。以下の属性を持つ
  - 職員 ID、イベント ID、従事可否、理由区分（休暇 / 育児・介護 / 健康上の配慮 / その他）、申告日時
  - 同一の（職員 ID, イベント ID）に対する再申告は履歴として保持し、最新の申告を有効とする（FR-04.5 の追加申告ループのため）
- **FR-02.8**: 従事可否申告を CSV / Excel から一括インポートできる。**本 PoC では、担当者が既存の手段（メール、Excel 回覧等）で収集した申告を代理で一括登録する。職員本人がシステムにログインして申告する機能は本 PoC の対象外とする**（A-08 を参照）

### FR-03: 距離・移動時間・移動費用の算出

- **FR-03.1**: 職員の居住小学校区の代表点と、施設の所在小学校区の代表点との間の**大円距離（Haversine 距離）**を算出する
- **FR-03.2**: 直線距離に**迂回係数**（既定値: 1.3）を乗じて実移動距離を近似する。迂回係数は担当者が設定できる
- **FR-03.3**: 実移動距離を**平均移動速度**（既定値: 30 km/h）で除して移動時間を算出する。平均移動速度は担当者が設定できる
- **FR-03.4**: 職員の居住小学校区と施設の所在小学校区が**同一**の場合、移動時間を固定値（既定値: 15 分）とする。この固定値は担当者が設定できる。距離 0 として扱わない
- **FR-03.5**: 移動費用は**距離帯モデル**で算出する。距離帯ごとに交通手段と費用の算出方式を切り替える。距離帯の境界値と各帯の費用は担当者が設定できる（NFR-M03）

  既定値（担当者が変更可能）:

  | 距離帯 | 交通手段 | 費用 |
  |-------|---------|------|
  | 2 km 未満 | 徒歩 | 0 円 |
  | 2 km 以上 10 km 未満 | 公共交通機関 | 一律 300 円 |
  | 10 km 以上 | タクシー | 実移動距離 × 400 円/km |

  **設計上の含意**: 距離帯モデルは非線形（階段関数）だが、**最適化問題の線形性は保たれる**。目的関数の費用項は `Σ c_ij · x_ij` であり、`c_ij` は職員 `i` と施設 `j` の組に対する定数として最適化の**前に**計算されるためである。したがって MILP ソルバーで扱える。

  **業務ルール**: 費用関数は距離に対して**単調非減少**でなければならない。距離帯の設定がこれに違反する場合（例: 遠くへ行くほど安くなる）、設定を拒否する。違反を許すと、最適化が「費用を下げるために、より遠い施設へ派遣する」という不合理な解を選びうる

- **FR-03.7**: 職員の居住小学校区と施設の所在小学校区が**同一**の場合、移動距離は 0 km、移動費用は 0 円とする。移動時間のみ固定値（FR-03.4）を用いる
- **FR-03.6**: 距離・移動時間・移動費用の算出はすべて**純粋関数**として実装し、外部 API に依存しない（オフライン動作可能）

### FR-04: 割当最適化

- **FR-04.1**: 指定されたイベントについて、職員を施設に割り当てる最適化計算を実行する。**最適化の対象となるのは、当該イベントに対し「従事可能」と申告した職員（FR-02.7）のみである**
- **FR-04.2**: 目的関数は以下の 3 項の重み付き和とし、これを最小化する。重み `w1, w2, w3` は担当者が画面から調整できる
  - 総移動時間（職員の負担）
  - 総移動費用（財政的コスト）
  - 不公平性の指標（最大移動時間、または移動時間の分散）
- **FR-04.3**: 以下の**ハード制約**（必ず満たす制約）を課す
  - **C1 定員充足**: 各施設に対し、必要人数がちょうど（または最低限）割り当てられる
  - **C2 一意割当**: 1 人の職員は、同一イベント内で高々 1 つの施設にのみ割り当てられる
  - **C3 職種・資格・役職**: 施設ごとに指定された職種・資格・役職の必要人数を満たす（例: 責任者は管理職に限る）
  - **C4 従事可否**: 当該イベントに対し「従事不可」と申告した職員（休暇、育児・介護、健康上の配慮）は割り当てない（FR-02.7）
  - **C5 部署継続性**: 同一部署から同時に割り当てる人数の上限を設ける（業務継続性の確保）
- **FR-04.4**: 以下の**ソフト制約**（可能な限り満たす制約。違反時はペナルティを目的関数に加算）を課す
  - **S1 従事履歴の平準化**: 直近のイベントで従事した職員を、可能な限り連続して割り当てない

#### FR-04.5: 実行不可能（infeasible）時の処理

最適化が実行不可能な場合、システムは**原因を診断し、原因に応じて振る舞いを分ける**。

| 原因 | システムの振る舞い |
|------|------------------|
| **従事可能職員の総数不足**（従事可能と申告した職員数 < 必要人数の総和） | 不足人数と、不足している施設を担当者に明示する。**C1（定員充足）は緩和しない**。担当者は人手による調整を行い、追加の従事可否申告を登録したうえで再最適化する（FR-06.6） |
| **職種・資格・役職（C3）の不足のみ**（総数は足りているが、特定施設の資格要件を満たす職員が足りない） | **C3 をソフト制約に降格**し、違反にビッグM（十分に大きな固定値）のペナルティを課して解を求める。解が存在するなら必ず C3 を満たす解が選ばれ、存在しない場合のみ最小限の違反を許す |
| **その他の制約（C2, C4, C5）による実行不可能** | 原因となった制約を明示する。これらは**降格しない**。C2 は物理的に降格不可能であり、C4 の降格は休暇中・健康上の配慮が必要な職員の派遣を意味し、C5 の降格は部署の業務停止を意味するため |

- **FR-04.5.1**: C3 を降格して得られた解については、**どの制約が何件違反されているかを一覧表示し、違反した割当行をハイライトする**
- **FR-04.6**: 最適化計算には制限時間を設け、制限時間内に厳密解が得られない場合は、その時点での最良の実行可能解と最適性ギャップを提示する

### FR-05: 現行方式との比較

#### FR-05.1: ベースラインの定義と比較の方法論

ベースラインは、**過去に実施したイベントの実際の割当実績**とする。比較は「過去イベントの再現」により行う。

- **FR-05.1.1**: 過去イベントの実績データ（イベント名、実施日、職員 ID → 施設 ID の対応、当時の従事可否申告）をインポートできる
- **FR-05.1.2**: 過去イベントの**各施設の必要人数**は、実績でその施設に割り当てられていた職員数として導出する
- **FR-05.1.3**: 過去イベントの**最適化対象職員集合**は、当該イベントに対し「従事可能」と申告した職員の集合とする（実際に割り当てられた職員の集合より広い）
- **FR-05.1.4**: 上記と同一の条件（同一の施設、同一の必要人数、同一の従事可能職員集合）で最適化を実行し、実績の割当と比較する。これにより、削減効果は**割当ルールの差のみに帰属**する
- **FR-05.1.5**: 職員の居住小学校区・所属部署・保有資格は、**現在の職員マスタの値**を使用する（当時の値は取得できない）。ベースラインと最適化結果の双方が同一の現在値で評価されるため、両者の差（削減効果）は妥当である。ただし絶対値は当時の実際の値と一致しない（A-09）
- **FR-05.1.6**: 過去の実績データが存在しない新規イベントについては、**担当者が手動でベースライン割当を入力できる**

- **FR-05.2**: ベースラインと最適化結果を比較し、以下の指標を提示する
  - 総移動時間（削減時間、削減率）
  - 総移動費用（削減額、削減率）
  - 最大移動時間（公平性の改善）
  - 移動時間の分布（ヒストグラム、または分位点）
- **FR-05.3**: 比較レポートを画面表示し、CSV としてエクスポートできる

### FR-06: 割当結果の確認と手動調整

- **FR-06.1**: 割当結果を一覧表示する（職員 → 施設、施設 → 職員 の双方向で参照可能）
- **FR-06.2**: 担当者は特定の職員の割当先を手動で変更できる
- **FR-06.3**: 手動変更後、ハード制約（C1〜C5）への違反を即座に検証し、違反があれば警告する
- **FR-06.4**: 手動変更した割当を固定（ピン留め）したうえで、残りの職員について再最適化を実行できる。**ピン留めがハード制約に違反する場合、再最適化を実行せずエラーとする**。担当者はピン留めを解除してから再実行する
- **FR-06.5**: 割当結果を CSV としてエクスポートできる
- **FR-06.6**: 追加の従事可否申告（FR-02.8）を登録したのち、再最適化を実行できる。担当者は以下のいずれかのモードを選択する
  - **全体再最適化**: 前回の割当を破棄し、従事可能な全職員を対象に最初から最適化する。最適な解が得られるが、既に内示を受けた職員の割当先が変わる可能性がある
  - **増分再最適化**: 前回の割当を固定（ピン留め）し、追加で従事可能になった職員のみを未充足の施設に割り当てる。既存の割当は変わらないが、全体最適にはならない

### FR-07: 監査とデータ整合性

- **FR-07.1**: 割当結果の作成・変更（誰が、いつ、何を、変更前後の値）を監査ログに記録する（SECURITY-13）
- **FR-07.2**: 認証失敗、認可違反、権限昇格の試行を監査ログに記録する（SECURITY-14）
- **FR-07.3**: 監査ログはアプリケーションから削除・改変できない追記専用ストレージに保管する（SECURITY-14）

## 4. 非機能要件（Non-Functional Requirements）

### 4.1 規模・性能

| ID | 要件 |
|----|------|
| NFR-P01 | 職員 500〜2,000 人、施設 50〜200 か所の規模を扱う（CQ3=B） |
| NFR-P02 | 割当最適化の計算時間は、上記規模において既定の制限時間（初期値: 300 秒）以内に実行可能解を返す |
| NFR-P03 | 距離行列の算出（最大 2,000 × 200 = 40 万要素）は事前計算しキャッシュする |
| NFR-P04 | CSV 一括インポートは 2,000 行を 30 秒以内に処理する |

**設計上の含意**: 決定変数は最大 2,000 × 200 = 40 万の 0-1 変数となる。厳密解法（MILP ソルバー）で解ける可能性はあるが、実用的な計算時間に収まるかは検証が必要である。NFR Requirements ステージで、厳密解法と発見的解法（貪欲法 + 局所探索、またはラグランジュ緩和）のトレードオフを評価すること。

### 4.2 セキュリティ

**セキュリティ拡張（security/baseline）は有効**。全 15 ルールがブロッキング制約として適用される。

### NFR-S10: デプロイ構成に伴うネットワーク境界の統制

#### PoC のデプロイ構成（本要件の対象）

本 PoC では、フロントエンドとバックエンドを**同一のインターネット側サーバー**上で稼働させる。庁内イントラネット PC から、このサーバーへアクセスする。庁外・自宅等からのアクセスは想定しない。

```text
+---------------------+                +--------------------------------+
|  Intranet PC        |                |  PoC Server (internet-side)    |
|  (municipal LAN)    |                |  +--------------------------+  |
|                     |    HTTPS       |  |  Frontend                |  |
|                     |--------------->|  +--------------------------+  |
|                     |                |  |  Backend (same host)     |  |
+---------------------+                |  +--------------------------+  |
                                       +--------------------------------+
   allowlist: municipal egress global IP
   + login restriction
```

本 PoC が実装すべき統制は以下の 2 点である。

| ID | 要件 | 対応 SECURITY ルール |
|----|------|---------------------|
| NFR-S10.1 | サーバーへのアクセスに**ログイン制限**を課す。未認証のリクエストは業務ロジックに到達してはならない（deny by default） | SECURITY-08 |
| NFR-S10.2 | サーバーは、**庁内イントラネットの出口グローバル IP アドレスからのアクセスのみ**を受け付ける。それ以外の送信元からの要求は拒否する | SECURITY-07 |

許可リストはハードコードせず、設定として外部化する（NFR-M03）。

**SECURITY-07 の文書化された例外**: SECURITY-07 は「公開ロードバランサの 80/443 以外に `0.0.0.0/0` からの受信を許可してはならない」と定める。本 PoC のサーバーはインターネット側に配置されるが、SECURITY-07 はルール自体が文書化された例外を許容している。本要件をその例外として記録する。**代償統制は NFR-S10.1（ログイン制限）と NFR-S10.2（庁内出口 IP の許可リスト）であり、この 2 統制により実質的な到達可能範囲は庁内イントラネットの認証済み利用者に限定される。**

**任意の追加強化策（本要件には含まないが推奨）**: WAF の導入。既存基盤がこれを提供している場合は活用する。

#### 実運用時のデプロイ構成（本 PoC の対象外）

実運用ではバックエンドを**庁内オンプレミス**に配置する。庁内サーバーをインターネットから到達可能にする仕組みは組織内に既に存在し（A-06）、それを利用する。この構成では、フロントエンドからバックエンドへ向かう通信に対し、**フロントエンドの送信元 IP アドレスによる追加の許可リスト制御**が必要になる。

この移行を手戻りなく行うため、PoC の設計段階から以下を課す（NFR-M05 を参照）。

- フロントエンドとバックエンドの境界を**明示的な API 境界**として設計する。同一ホスト上で稼働していても、プロセス内の直接呼び出しで結合してはならない
- バックエンドのエンドポイント URL は設定として外部化し、ホスト分離時にコード変更を要さないこと

## 8. 要件サマリ

本プロジェクトは、自治体における**災害時避難所応援職員の割当**を、職場単位から**居住地考慮型の数理最適化**に置き換える PoC である。

業務フローは次のとおりである。担当者がイベントを登録し、職員が従事可否を申告し（PoC では担当者が代理で CSV 一括登録）、従事可能と申告した職員を対象に割当最適化を実行する。人員が不足した場合は人手による調整を経て追加の従事可否申告を登録し、再最適化する。

中核となるのは、職員を施設に割り当てる**一般化割当問題**の求解である。目的関数は総移動時間・総移動費用・公平性の重み付き和であり、重みは担当者が調整できる。定員充足、一意割当、職種・資格、従事可否、部署継続性の 5 つのハード制約と、従事履歴の平準化というソフト制約を課す。実行不可能な場合は原因を診断し、職種・資格（C3）の不足のみが原因であれば C3 をビッグMペナルティ付きのソフト制約に降格して解を求める。従事可能職員の総数が不足している場合は定員充足（C1）を緩和せず、追加申告を求める。

距離は小学校区の代表点（= 小学校の所在地座標）間の Haversine 距離に迂回係数を乗じて近似し、外部 API に依存しない。同一校区内の移動は固定時間として扱う。

システムは、過去に実施したイベントの実際の割当実績をベースラインとし、同一条件（同一施設、同一必要人数、同一の従事可能職員集合）で最適化を再実行して比較レポート（総移動時間・総移動費用の削減効果）を出力する。これにより削減効果は割当ルールの差のみに帰属する。担当者は結果を手動修正し、修正を固定したまま再最適化できる。

個人情報を扱うためセキュリティ拡張を全面適用し、割当アルゴリズムの正当性を担保するためプロパティベーステスト拡張を全面適用する。レジリエンシー拡張は PoC のスコープ外として次フェーズに延期する。

**設計上の重要な留意点**:

1. ~~**A-04（費用の線形モデル）**は「タクシー費用の高額化」の非線形性を捉えない~~ → **v1.4 で解決済み。** U-02 の Functional Design で距離帯モデルへ変更した。「距離帯モデルは非線形だから MILP で扱えない」という懸念は成立しない。費用は最適化の**前に**計算される定数係数であり、目的関数は決定変数について線形のままである
2. **NFR-S10（デプロイ構成）**は、ログイン制限（NFR-S10.1）と庁内出口 IP の許可リスト（NFR-S10.2）を代償統制とする SECURITY-07 の文書化された例外である。本 PoC ではフロントエンドとバックエンドが同一サーバーに同居するため、インターネットに露出する境界は 1 つのみである。**実運用ではバックエンドがオンプレミスへ分離される**ため、NFR-M05（明示的な API 境界）を設計段階から遵守しないと移行時に手戻りが生じる
3. **NFR-P02（計算時間）**は最大 40 万の 0-1 変数を扱う。厳密解法の実用性は NFR Requirements ステージで検証すること
