## 1. 目的とスコープ

本ステージでは、**高レベルのコンポーネント識別とサービス層の設計**を行う。

**本ステージで扱うこと**:
- 主要な機能コンポーネントとその責務の識別
- コンポーネントのインターフェース定義（メソッドシグネチャ、入出力の型）
- サービス層のオーケストレーション設計
- コンポーネント間の依存関係と通信パターン

**本ステージで扱わないこと**:
- 詳細なビジネスロジック（Functional Design、CONSTRUCTION フェーズ、ユニットごと）
- 技術スタック（プログラミング言語、フレームワーク、ソルバー、DB 製品）の決定 → **NFR Requirements ステージ**（Q12=D、execution-plan.md H-3, H-4）
- インフラ構成の具体化（Infrastructure Design ステージ）

したがって、以下の質問は**言語・製品に依存しない構造的な決定**に絞る。

### Question 1: アーキテクチャスタイル（Design Patterns）

コンポーネントの依存方向をどう定めますか？ これは NFR-M01（アルゴリズム差し替え）と NFR-M02（純粋関数）の実現方法を左右します。

A) **レイヤードアーキテクチャ** — プレゼンテーション層 → アプリケーション層 → ドメイン層 → インフラ層 の一方向依存。理解しやすいが、ドメイン層がインフラ層（DB、ソルバー）に依存しがちで、最適化アルゴリズムの差し替えが困難になりやすい

B) **ヘキサゴナルアーキテクチャ（ポート＆アダプタ）** — ドメイン層が中心に位置し、外部（DB、ソルバー、CSV、Web）はすべてポート（インターフェース）を介したアダプタとして接続する。最適化ソルバーを「ポートの背後のアダプタ」とすることで、厳密解法と発見的解法を差し替え可能にする。距離算出は純粋関数としてドメイン層の内側に置ける **（推奨。NFR-M01 と NFR-M02 を構造的に強制できる）**

C) **シンプルな MVC / サービス層のみ** — PoC の速度を優先し、構造を最小限にする。NFR-M01 と NFR-M02 は規約（コーディング規則）で担保する

### Question 2: 最適化計算の実行方式（Component Methods / Service Layer）

**これが本ステージで最も重要な設計判断です。**

NFR-P02 により、割当最適化は最大 300 秒（5 分）を要します。一般的な HTTP リクエストのタイムアウトは 30〜60 秒であり、同期的な API 呼び出しでは応答を返せません。

A) **同期 API** — クライアントが最適化 API を呼び出し、計算完了まで接続を保持する。タイムアウトを 300 秒以上に延長する。実装は単純だが、ブラウザ・リバースプロキシ・ロードバランサのいずれかがタイムアウトする危険がある。担当者は計算中、画面を離れられない

B) **非同期ジョブ + ポーリング** — 最適化 API はジョブ ID を即座に返す。バックエンドはバックグラウンドで計算し、クライアントは定期的にジョブの状態を問い合わせる。担当者は進捗（経過時間、現在の最適性ギャップ）を確認でき、画面を離れることもできる **（推奨。US-20「制限時間内に厳密解が得られない場合、その時点での最良解と最適性ギャップを提示する」を自然に実現できる）**

C) **非同期ジョブ + サーバー送信イベント（SSE）/ WebSocket** — サーバーから進捗をプッシュする。ポーリングより効率的だが、実装が複雑で、リバースプロキシの設定に依存する

### Question 3: 最適化ジョブのキャンセルと同時実行（Service Layer Design）

Question 2 で B または C を選択した場合、以下も確定する必要があります。

A) **同一イベントに対する最適化ジョブは同時に 1 つのみ。実行中のジョブはキャンセルできる** **（推奨。担当者が重みを変えて試行錯誤する際、前のジョブを止められる）**

### Question 4: 距離行列のキャッシュ配置（Component Identification）

NFR-P03 により、距離行列（最大 40 万要素）は事前計算してキャッシュします。距離は「小学校区 × 小学校区」の組で決まるため、実際のキャッシュ対象は職員 × 施設ではなく**小学校区 × 小学校区**（例: 100 校区なら 1 万要素）に圧縮できます。

キャッシュをどこに置きますか？

A) **小学校区ペア単位で永続化する（DB テーブル）** — 小学校区マスタが更新されたときのみ再計算する。プロセス再起動後もキャッシュが残る **（推奨。校区数は職員数より 1〜2 桁小さいため、40 万要素ではなく 1 万要素程度に収まる）**

B) **プロセス内メモリにキャッシュする** — 高速だが、プロセス再起動のたびに再計算が必要。バックエンドを複数プロセスで動かす場合、各プロセスが重複して保持する

C) **キャッシュせず、毎回計算する** — Haversine 距離の計算は軽量であり、40 万回の計算でも数秒で終わる可能性がある。NFR-P03 を満たさないが、実測次第では許容できる

### Question 6: 監査ログの保存先（Component Identification / SECURITY-14）

SECURITY-14 は「監査ログは追記専用または改竄検知可能なストレージに保管し、アプリケーションが自身のログを削除・改変できないこと」を要求します。US-04 の受入基準でもあります。

A) **業務 DB とは別のストレージに追記専用で書き込む（別 DB、または OS レベルで追記専用としたファイル）。アプリケーションのアカウントに削除権限を与えない** **（推奨。SECURITY-14 を素直に満たす）**

## 3.5 フォローアップ質問（Step 9: 回答分析の結果）

ご回答を分析しました。**Q1〜Q8、Q10 の 9 件は明確で、相互に矛盾せず、そのまま設計に使用できます。**

一方、**Question 9 = B** には重大な問題があります。以下を確認させてください。

---

### 検出された矛盾: Question 9 = B

Q9 = B は「**比較レポートコンポーネントが独自の最適化ロジックを持つ**」という選択です。これを採用すると、以下が生じます。

#### 問題 1: 成功基準 SC-01 が成立しなくなる（最も重大）

FR-05（比較レポート）は「**このシステムの割当ルールが、過去の実績と比べてどれだけ削減できるか**」を示すために存在します。

比較レポートが**別の最適化ロジック**で計算した場合、レポートに表示される削減効果は、**実際にこのシステムが生成する割当とは別物**になります。上長・関係部署に提示する数値が、システムが実際に出す結果と一致しません。これは PoC の第一目的（SC-01）を無効化します。

#### 問題 2: Q1 = B（ヘキサゴナルアーキテクチャ）と矛盾する

Q1 でヘキサゴナルアーキテクチャを選択されたのは、ソルバーをポートの背後に置いて差し替え可能にするためです。比較レポート内にソルバーロジックを複製すると、このポート抽象が意味を失います。

#### 問題 3: NFR-M01 と矛盾する

NFR-M01 は「最適化エンジンをドメインロジックから分離し、アルゴリズムを差し替え可能にする」と定めています。独立した 2 つのオプティマイザが存在すると、差し替えを 2 回行う必要があり、やがて実装が乖離します。

#### 問題 4: INV-12 / PBT-05 の検証が片方にしか及ばない

総当たり法をオラクルとする検証（PBT-05）は、2 つのうち片方のオプティマイザしか検証しません。

#### 補足: 選択肢 A は「比較レポートに独自の責務がない」という意味ではありません

選択肢 A を選んでも、比較レポートコンポーネントは以下の独自の責務を持ちます。

- 過去イベントの条件を組み立てる（施設一覧、実績からの必要人数の導出、従事可能職員集合の特定）
- 実績の割当と最適化結果の差分（削減時間、削減額、削減率、最大移動時間、分布）を算出する
- レポートを画面表示し、CSV にエクスポートする

**A が求めるのは「実際の最適化計算そのものは、共有された単一のエンジンに委譲する」という 1 点のみ**です。

もし Q9 = B を「比較レポートが独自の**比較・再現ロジック**を持つ」という意味で選ばれたのであれば、それは選択肢 A に含まれます。
