# ビジネスルール — U-06 `security`

**作成日**: 2026-07-17
**ステージ**: CONSTRUCTION - Functional Design（ユニット 6 / 8）

---

## 1. 認証のルール（SEC-01）

### BR-SEC01: deny by default（US-01, NFR-S04/S10.1, SECURITY-08）
すべてのエンドポイントは既定で認証を要求する。**未認証の要求は業務ロジックに到達してはならない**。セッション ID が無い・不明・期限切れ・失効済みのいずれも**拒否**。

### BR-SEC02: 担当者ロールのみ、管理者ロールを設けない（Q1=A）
本 PoC のアプリケーションに**管理者ロールを設けない**。アカウント発行は OS 権限を持つ運用者の作業（CLI / 初期投入）。したがって **SECURITY-12 の「管理者アカウントは MFA 必須」は適用対象が存在せず N/A** である。ロールは列挙型とし、将来 `STAFF`（職員本人, A-08）を追加できる形にする。

### BR-SEC03: パスワードは適応型ハッシュで保存（SECURITY-12）
平文・可逆暗号・単純ハッシュで保存しない。適応型ハッシュ（Argon2 / bcrypt 等）を用いる。製品と各パラメータは NFR Requirements で決定（U06-H1）。

### BR-SEC04: 認証失敗の応答は汎用（SECURITY-09）
利用者名の存在有無・ロック状態を**応答から推測させない**。失敗理由は監査ログに記録し、応答は汎用メッセージのみ。

### BR-SEC05: アカウントロック（MU-03, SECURITY-12）
連続する認証失敗が閾値に達したら、アカウントをロックする（または漸増遅延を課す）。成功時に失敗回数をリセットする。閾値・解除方法は NFR Requirements で決定。

### BR-SEC06: セッションは不透明・失効可能（Q2=A）
セッション ID はランダムな不透明値とする。**JWT を使わない**——ログアウト・権限変更の失効を即時に効かせるため。保存は `SessionStorePort`（U-07 が DB 実装を注入）。期限切れは拒否。

---

## 2. 認可のルール（SEC-02）

### BR-SEC07: ロール + オブジェクトレベル認可の関門（Q3=A, MU-01, NFR-S04）
リソース ID を参照するすべての要求は、`authorize_resource_access(principal, resource)` を**必ず経由する**。PoC では担当者が全イベントにアクセス可だが、**関門を省略しない**——将来（A-08）の「本人の申告のみ」への絞り込みを後付けすると漏れるため。

### BR-SEC08: deny by default（認可）
未知のロール・未知のアクション・判定不能はすべて**拒否**。許可は明示的な規則がある場合のみ。

### BR-SEC09: 認可違反の記録（FR-07.2）
認可違反・権限昇格の試行を監査ログに記録する。

---

## 3. ネットワーク統制・レート制限のルール

### BR-SEC10: IP 許可リスト（US-02, NFR-S10.2, SECURITY-07 の代償統制）
庁内イントラネットの**出口グローバル IP からの要求のみ**を受け付ける。それ以外は拒否し、業務ロジックに到達させない。**許可リストはハードコードせず設定として外部化**（NFR-M03）。

### BR-SEC11: レート制限（NFR-S09, MU-03）
公開エンドポイントにレート制限を課す。単一サーバー・単一ワーカー（A-07）のため**インメモリ**カウンタで実現する。超過は拒否。

### BR-SEC12: パイプライン順序（Q6=A）
**SEC-03 IP → SEC-04 レート制限 → SEC-01 認証 → SEC-02 認可 → SEC-05 入力検証**。安価で広範な拒否を先に置く。**U-07 がこの順序で配線する**（U06-H4）。

---

## 4. 入力検証のルール（SEC-05）

### BR-SEC13: CSV 数式インジェクションの無害化（MU-02, U03-H5）
CSV **エクスポート**時、値が `=`, `+`, `-`, `@` で始まる場合、先頭に `'` を付す。**U-03 `serialize_csv` / U-05 `export_report_csv` の注入口に U-07 が `sanitize_csv_cell` を注入する**。U-03/U-05 は U-06 に依存しない。

### BR-SEC14: 入力検証（SECURITY-05）
長さ・書式などの再利用可能な検証関数を提供する。API 境界の検証は U-07 の Pydantic と併用する。

---

## 5. 監査のルール（S-08 / P-04 / A-05）

### BR-SEC15: 記録対象（FR-07.1/7.2, SECURITY-13/14）
(1) 割当結果の作成・変更（**誰が / いつ / 何を / 変更前後の値**）、(2) マスタの変更・削除、(3) 認証失敗・認可違反・権限昇格の試行。

### BR-SEC16: 監査ログに個人情報を含めない（SECURITY-03, **U01-H22**）
職員 ID・イベント ID・施設 ID のみを記録する。**氏名・居住小学校区を含めない**。特に **`reason_category`（休暇・育児介護・健康上の配慮）は監査ログに出さない**（U01-H22）——要配慮個人情報に近く、監査の目的にも不要である。**パスワードを記録しない**。

**例**:
- ✅ `{"ts":"2026-07-17T00:00:00Z","actor":"C001","action":"ASSIGNMENT_CHANGED","event_id":"E1","staff_id":"S001","before":{"facility_id":"F03"},"after":{"facility_id":"F07"}}`
- ❌ `{"actor":"鈴木","staff_name":"山田太郎","reason":"健康上の配慮"}`

### BR-SEC17: 追記専用（US-04, MU-04, SECURITY-14）
監査ログは **OS レベルの追記専用ファイル**（`chattr +a`）に保管する。**アプリケーションから削除・改変できない**。アプリアカウントは追記のみ。ローテーションは特権 cron（別アカウント）が実施する。

### BR-SEC18: 監査は業務トランザクションの外側（SECURITY-14）
業務トランザクションがロールバックされても、監査記録は残る。

### BR-SEC19: 形式（FR-07）
JSON Lines、**UTC** タイムスタンプ（ISO 8601）。

## 6. 全体のルール

### BR-SEC20: fail closed（SECURITY-15）
判定不能・設定不備・ポート未注入・例外のいずれの場合も、**拒否側に倒す**。「検証できないので通す」という分岐を作らない。

### BR-SEC21: エラー応答に内部情報を含めない（SECURITY-09）
スタックトレース・内部パス・フレームワークバージョンを応答に含めない（応答の生成は U-07 の責務だが、U-06 の例外は汎用メッセージ + 構造化文脈（PII なし）に限る）。

---

## 7. 悪用ケースへの対策（MU-01〜MU-04）

| 悪用ケース | 対策 | ルール |
|-----------|------|-------|
| **MU-01** IDOR による他人の割当情報の閲覧 | オブジェクトレベル認可の関門を必ず経由 | BR-SEC07/08 |
| **MU-02** CSV の数式インジェクション | エクスポート時のサニタイズ（U-07 が注入）| BR-SEC13 |
| **MU-03** 総当たりによるログイン突破 | IP 許可リスト + レート制限 + アカウントロック + 監査アラート | BR-SEC05/10/11 |
| **MU-04** 監査ログの隠蔽 | OS レベル追記専用（アプリに削除権限なし）| BR-SEC17 |

## 8. 拡張ルール適合サマリ

**U-06 は SECURITY 拡張の実体を担うため、全 15 ルールを詳細に評価する。**

| ルール | 判定 | 根拠 |
|--------|------|------|
| **SECURITY-01** 保存時暗号化 | ✅ 適合（インフラ）| 暗号化ボリューム（U-01）。U-06 のセッション/監査もその上 |
| **SECURITY-02** 転送時暗号化 | ✅ 適合（インフラ）| 既存公開基盤の TLS 終端（H-6 discharged, U-01）|
| **SECURITY-03** ログに PII を含めない | ✅ **適合** | BR-SEC16。監査ログから氏名・居住地・`reason_category` を除外（U01-H22）|
| **SECURITY-04** セキュリティヘッダ | N/A（U-07）| HTML/HTTP 応答は U-07 の責務 |
| **SECURITY-05** 入力検証・パラメータ化 | ✅ **適合** | BR-SEC13/14。SQL は U-03 が Core でパラメータ化済み |
| **SECURITY-06** 秘密情報の管理 | ✅ 適合 | パスワードハッシュ・セッション ID をログに出さない。設定は外部化（NFR-M03）|
| **SECURITY-07** ネットワーク境界 | ✅ **適合（文書化された例外 + 代償統制）** | BR-SEC10（庁内出口 IP 許可リスト）+ BR-SEC01（ログイン制限）。requirements.md NFR-S10 に例外を記録済み |
| **SECURITY-08** 既定で認証・認可 | ✅ **適合** | BR-SEC01/07/08。deny by default |
| **SECURITY-09** エラー応答 | ✅ 適合 | BR-SEC04/21。汎用メッセージ、内部情報を出さない |
| **SECURITY-10** サプライチェーン | ✅ 適合 | ハッシュライブラリ等をバージョン固定（NFR Requirements, U06-H1）|
| **SECURITY-11** 認証・認可の分離 + レート制限 | ✅ **適合** | 認証・認可は専用モジュール（SEC-01/SEC-02）。BR-SEC11 |
| **SECURITY-12** MFA + 適応型ハッシュ | ✅ **適合（MFA は N/A）** | BR-SEC03（適応型ハッシュ）、BR-SEC05（ロック）。**MFA は「管理者アカウントが存在しない」ため適用対象なし**（BR-SEC02, Q1=A）。実運用で管理者ロールを設ける際は MFA が必須（U06-H5）|
| **SECURITY-13** データ完全性 | ✅ **適合** | BR-SEC15（変更前後の値を監査）|
| **SECURITY-14** 監査ログの保護 | ✅ **適合** | BR-SEC17/18。OS レベル追記専用、アプリに削除権限なし |
| **SECURITY-15** fail closed | ✅ **適合** | BR-SEC20。全関門が拒否側に倒れる |

**ブロッキング所見: なし**

**SECURITY-12 の N/A 判定について**: これは免除ではない。**管理者アカウントというルールの適用対象そのものが本 PoC のアプリケーションに存在しない**（Q1=A）ためである。アカウント発行は OS 権限を持つ運用者の作業であり、アプリケーションの認証境界の外にある。実運用で管理者ロールを設ける場合は MFA の実装が必須であり、U06-H5 として申し送る。
